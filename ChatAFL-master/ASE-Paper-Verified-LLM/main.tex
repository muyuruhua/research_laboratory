\begin{abstract}
Stateful protocol fuzzing is difficult because a message can be syntactically fluent yet invalid for the live session state. This problem becomes sharper when large language models (LLMs) are inserted directly into the fuzzing loop. We present LoopFuzz, a closed-loop runtime admission-control design for LLM-guided stateful protocol fuzzing. LoopFuzz treats LLM outputs as bounded hypotheses rather than directly admissible inputs. It derives message hypotheses from seed traces and observed responses, checks candidate interventions through runtime admission control over parseability, response-grounded acceptability, state reachability, and downstream gain, and uses counterexample-guided local refinement to repair failed hypotheses. LoopFuzz further couples admission control with state-aware scheduling so that model assistance is triggered only under adaptive plateau conditions and is steered toward underexplored inferred protocol-state-machine frontier states. We evaluate LoopFuzz on a 10-target benchmark suite with repeated 24-hour campaigns. On the nine off-the-shelf targets with complete primary 10-run comparisons against AFLNet and ChatAFL, LoopFuzz attains the highest mean final code-edge coverage on all nine targets and the highest mean final IPSM-edge count on all nine targets. Exact two-sided Mann-Whitney U testing shows code-edge gains versus both primary baselines on ProFTPD, Pure-FTPd, Exim, Forked-daapd, and Lighttpd1, and IPSM-edge gains on LightFTP, bftpd, ProFTPD, Pure-FTPd, Exim, Live555, and Kamailio. A matched-support Mosquitto case also favors LoopFuzz over AFLNet and ChatAFL, but auxiliary coverage-only comparisons against NSFuzz and MBFuzzer are mixed, so our strongest claim is robustness over the closest implementation-lineage baselines rather than blanket superiority over specialized external fuzzers.
\end{abstract}

\section{Introduction}
Network protocol implementations remain difficult security targets because correctness depends on interaction history rather than isolated inputs~\cite{aflnet,stateafl,sgf_usenix22,formatted_stateful_greybox_fuzzing_2024,resolverfuzz_query_response_2024}. An FTP server, for example, rejects a well-formed \texttt{PASS} command if no valid \texttt{USER} command has established the login state. Unlike file fuzzing, protocol fuzzing must preserve message syntax, temporal order, and request-response progress across a multi-step session~\cite{resolverfuzz_query_response_2024,mbfuzzer_mqtt_2025,bleem_packet_sequence_2023,logos_log_guided_fuzzing_2024,diane_identifying_fuzzing_triggers_2021,corecrisis_context_aware_2025}.

Traditional coverage-guided fuzzers work well for stateless parsers. They fit network servers poorly when later behavior depends on earlier valid exchanges~\cite{directed_greybox_fuzzing_2017,seed_selection_successful_fuzzing_2021,one_fuzzing_strategy_rule_2022,regression_greybox_fuzzing_2021,efficient_errors_2022}. Stateful greybox fuzzers such as AFLNet and StateAFL partially close this gap. They infer progress from responses and replay valid traces~\cite{aflnet,stateafl,sgf_usenix22,profuzzbench_benchmark_stateful_protocol_2021,snapfuzz_high_throughput_fuzzing_2022,bleem_packet_sequence_2023,formatted_stateful_greybox_fuzzing_2024}. Even so, byte-level mutation still struggles to synthesize the context-sensitive messages needed to cross deep protocol boundaries.

Large language models offer a plausible source of such messages. ChatAFL and later LLM-assisted fuzzers show that a model can extract structure from specifications, logs, or documentation and produce fluent candidates~\cite{chatafl,fuzz4all_universal_fuzzing_large_2024,llmif_augmented_large_language_2024,matter_llm_specification_2024,carpetfuzz_documentation_2023,prompt_fuzzing_fuzz_driver_2024,large_language_models_are_2023,large_language_models_are_2024}. But fluency is not enough. A request can be grammatically plausible and still be invalid for the live session state. Such executions spend budget without improving queue quality.

LoopFuzz places a runtime admission controller between LLM generation and queue admission. It treats the LLM as a hypothesis generator rather than an oracle. It derives message hypotheses from RFC fragments, seed traces, and observed responses. It stores failed executions as counterexamples and uses them for CEGR rather than unconstrained regeneration. It also uses inferred protocol state machine (IPSM) feedback to prioritize frontier states and rare transitions, and to trigger assistance only when ordinary mutation stalls. The name \emph{LoopFuzz} emphasizes closed-loop admission and refinement, avoiding any suggestion of formal verification of protocol semantics, model behavior, or server correctness.

The contributions of this paper are as follows:
\begin{itemize}
    \item \textbf{Hypothesis-Driven Message Modeling.} LoopFuzz derives message grammars and field constraints from RFC fragments, seed traces, and observed responses, and maintains them as explicit runtime hypotheses.
    \item \textbf{A Closed-Loop Runtime Admission Boundary.} LoopFuzz inserts a runtime admission controller between the LLM and the queue. The controller checks parseability, response-grounded acceptability, state reachability, and downstream gain before admission.
    \item \textbf{Counterexample-Guided Local Refinement.} LoopFuzz preserves failed request-response traces as counterexamples and uses them to patch one field constraint or production at a time, which constrains model freedom and stabilizes refinement.
    \item \textbf{State-Aware Scheduling.} LoopFuzz leverages IPSM topology, state productivity, and adaptive plateau detection to prioritize underexplored frontier states and to request model assistance only when mutation alone stalls.
    \item \textbf{An Empirical Study of Runtime-Validated Assistance.} We evaluate LoopFuzz on a 10-target benchmark suite with repeated 24-hour campaigns, including nine off-the-shelf 10-run primary comparisons against AFLNet and ChatAFL, a matched-support Mosquitto case, auxiliary target-specific coverage comparisons against NSFuzz and MBFuzzer, and code-driven ablations of the shipped controller.
\end{itemize}

Accordingly, the paper evaluates LoopFuzz as a campaign-control policy, not as a standalone message generator. In stateful protocol fuzzing, generation matters only when it survives runtime evidence and improves downstream queue quality.

\subsection{Coverage-Guided Fuzzing vs. Network Targets}
A coverage-guided fuzzer operates through a repeated feedback cycle of seed selection, mutation, execution, coverage measurement, and novelty-based queue update~\cite{seed_selection_successful_fuzzing_2021,one_fuzzing_strategy_rule_2022,regression_greybox_fuzzing_2021,efficient_errors_2022}.
This loop is effective for file parsers, but network targets impose three constraints that matter here:
\begin{enumerate}
    \item \textbf{Temporal state dependence:} server behavior depends on the order and semantics of earlier messages, not only on the current payload~\cite{aflnet,stateafl,sgf_usenix22,formatted_stateful_greybox_fuzzing_2024}.
    \item \textbf{Format rigidity:} protocols require strict delimiters, field layouts, and often checksum or length consistency, so many mutated messages die before they reach deeper logic~\cite{gramatron_effective_grammar_aware_2021,griffin_grammar_free_dbms_2022,formatted_stateful_greybox_fuzzing_2024}.
    \item \textbf{Execution instability:} sockets, forking daemons, and asynchronous response handling complicate both coverage collection and campaign throughput~\cite{snapfuzz_high_throughput_fuzzing_2022}.
\end{enumerate}

\subsection{Stateful Greybox Fuzzing (SGF)}
SGF addresses this gap by treating the target as an \emph{inferred protocol state machine} (IPSM). Formally, the IPSM can be viewed as a Mealy machine $M = (Q, I, O, \delta, \lambda, q_0)$, where:
\begin{itemize}
    \item $Q$ is the set of inferred protocol states;
    \item $I$ is the set of client messages;
    \item $O$ is the set of observed server responses;
    \item $\delta$ maps a state and input to a successor state;
    \item $\lambda$ maps a state and input to an observed response; and
    \item $q_0$ is the initial connection state.
\end{itemize}

AFLNet-style fuzzers infer $Q$ from observed responses and use that structure to bias later exploration toward rare or promising parts of the protocol. Here, the IPSM matters for one reason. It gives LoopFuzz a notion of progress that is richer than raw edge coverage alone.

\subsection{LLM Integration into Protocol Fuzzing}
Large language models make it easier to propose structure-aware protocol messages from RFC text, interaction history, or observed responses. That helps with syntax and message diversity, but it does not solve the harder control problem: a fluent request can still be wrong for the live session state.

\subsection{A Motivating Example: Semantic Drift}

\begin{figure}[htbp]
\centering
\includegraphics[width=\columnwidth]{figures/motivation.pdf}
\caption{An example of semantic drift where a fluent request violates protocol state preconditions, contrasting open-loop admission with LoopFuzz's runtime-validated rejection and refinement.}
\label{fig:motivation}
\end{figure}

Consider an FTP fuzzing campaign against ProFTPD, as illustrated in Fig.~\ref{fig:motivation}. The fuzzer executes \texttt{USER} and \texttt{PASS}. It then queries the LLM for the next request, and the model returns \texttt{RETR example\_file.txt}. The request is syntactically fluent but semantically premature. The client lacks an active data channel via \texttt{PASV} or \texttt{PORT}. The server rejects it with \texttt{425 Use PORT or PASV first}.

An open-loop LLM fuzzer admits this \texttt{RETR} request because it looks fluent. This is \emph{semantic drift}. The request is locally plausible, but it violates the protocol precondition for the current session state. The fuzzer then mutates a rejected branch instead of crossing the missing state transition. LoopFuzz blocks this drift. The runtime admission controller treats the \texttt{425} reply as negative evidence, rejects the candidate, and records the failed trace as a counterexample. CEGR then repairs the missing state precondition instead of regenerating the full continuation. This example captures the paper's central claim: in stateful protocol fuzzing, the value of LLM assistance depends on closed-loop runtime admission, not on surface fluency. In the current draft, we use semantic drift as an operational motivation for rejection and CEGR repair, not as a separately estimated global rate.
\section{Related Work}
We position LoopFuzz against the prior lines that are closest in mechanism and evaluation.

Earlier structure-aware fuzzing used explicit message structure, inferred snippets, token constraints, or grammar-level guidance to preserve validity~\cite{snipuzz_black_box_fuzzing_2021,token_level_fuzzing_2021,gramatron_effective_grammar_aware_2021,griffin_grammar_free_dbms_2022,no_grammar_no_problem_2023,likely_invariants_feedback_2021,mundofuzz_grammar_inference_2022}. These systems improve input quality. They do not address the control problem that arises when an external model proposes state-dependent protocol messages.

Stateful greybox fuzzing addresses protocol interaction more directly. AFLNet, StateAFL, and the broader SGF line infer IPSM structure from server behavior and prioritize rare or productive traces~\cite{aflnet,stateafl,sgf_usenix22,profuzzbench_benchmark_stateful_protocol_2021}. Later systems extend this idea to packet-sequence exploration, format-sensitive protocol fuzzing, and communication-heavy environments~\cite{bleem_packet_sequence_2023,formatted_stateful_greybox_fuzzing_2024,logos_log_guided_fuzzing_2024,msgfuzzer_message_sequence_guided_2024,resolverfuzz_query_response_2024,mbfuzzer_mqtt_2025,fuzzusb_hybrid_stateful_fuzzing_2022,dtls_fuzzer_dtls_protocol_2022,edhoc_fuzzer_edhoc_protocol_2023,tron_fuzzing_linux_network_2025}. LoopFuzz builds on this line, but adds a runtime-validated admission boundary for LLM interventions. SGF, Bleem, Logos, and MBFuzzer are therefore important external comparison points beyond AFLNet and ChatAFL; our current artifact-level evaluation does not yet include direct head-to-head reproduction against that broader set, and we treat that omission as a limitation rather than as evidence that those systems are weaker.

Adjacent work studies state-aware or interaction-heavy fuzzing in robotic policies, firmware, Linux drivers, data-distribution middleware, hardware, and embedded systems~\cite{pgfuzz_policy_guided_fuzzing_2021,android_smarttvs_vulnerability_discovery_2021,fuzzware_mmio_2022,statefuzz_linux_driver_2022,differential_fuzzing_data_distribution_2024,fuzzing_hardware_like_software_2022,coverage_guided_fuzzing_embedded_2023}. These systems are not protocol fuzzers in the narrow sense. They still support the broader point that state feedback and interaction context can dominate raw mutation quality.

Target-aware scheduling and semantic validation form another relevant line. Directed greybox fuzzing studies how to steer search toward high-value targets~\cite{directed_greybox_fuzzing_2017,windranger_blocks_2022,when_analysis_2025}. Work on seed selection and strategy adaptation studies how to spend budget more effectively~\cite{seed_selection_successful_fuzzing_2021,one_fuzzing_strategy_rule_2022,regression_greybox_fuzzing_2021,efficient_errors_2022}. Semantic validation and fuzz-driver generation show that stronger inputs often require an explicit acceptance interface~\cite{one_engine_to_fuzz_em_all_2021,apicraft_fuzz_driver_2021}. LoopFuzz inherits that lesson and applies it to LLM proposals.

Related work also studies how to infer dependencies or exploit guidance from data-flow and learned signals outside protocol fuzzing proper~\cite{rulf_rust_library_fuzzing_2021,smartian_analyses_2021,magneto_step_wise_approach_2024}. This line reinforces our decision to treat the LLM as a bounded proposal mechanism rather than as an unconstrained generator.

LLM-assisted fuzzing attacks the synthesis bottleneck more directly. ChatAFL uses RFCs and interaction histories to generate protocol messages~\cite{chatafl}. Adjacent systems use LLMs for general fuzz input generation, documentation-guided constraint extraction, specification-guided device fuzzing, or fuzz-driver generation~\cite{fuzz4all_universal_fuzzing_large_2024,llmif_augmented_large_language_2024,matter_llm_specification_2024,docter_documentation_guided_fuzzing_2022,carpetfuzz_documentation_2023,prompt_fuzzing_fuzz_driver_2024}. Our work is closest to ChatAFL. The difference is the control boundary. LoopFuzz asks whether a proposal should be admitted, whether its hypothesis survives runtime evidence, and how the IPSM should guide the next query.

Benchmarking practice is also part of the context. ProFuzzBench established a reusable baseline for repeated protocol-fuzzing experiments~\cite{profuzzbench_benchmark_stateful_protocol_2021}. Recent methodology work shows how easily comparisons become unstable without fixed budgets, repeated trials, and careful interpretation of coverage signals~\cite{sok_prudent_evaluation_practices_2024,reliability_benchmarking_2022,many_stack_2022}. We follow that guidance because runtime-validated assistance is especially sensitive to campaign history.

\section{LoopFuzz Design}

Fig.~\ref{fig:arch} summarizes the three coupled loops in LoopFuzz: the Grammar Hypothesis Loop, the Fuzz Execution Loop, and the LLM Intervention Loop.

\begin{figure*}[htbp]
\centering
\includegraphics[width=\textwidth]{figures/fig1.pdf}
\caption{Control architecture of LoopFuzz. The Grammar Hypothesis Loop maintains message hypotheses, the Fuzz Execution Loop updates coverage and IPSM feedback, and the LLM Intervention Loop proposes bounded interventions; a Runtime Verifier mediates admission before any proposal can affect the queue.}
\label{fig:arch}
\end{figure*}

LoopFuzz preserves the stateful greybox fuzzing execution path. It sets a strict control boundary between LLM generation and queue admission. A model output changes the campaign only after runtime evidence supports admission. The admission rule checks message structure, parseability, response behavior, inferred state reachability, and downstream campaign value. The method has four coupled components: grammar hypothesis generation, runtime admission control, CEGR, and state-aware scheduling.

This control boundary is the core idea of the paper. ChatAFL is open-loop: it uses a fixed trigger, a plain-text prompt, and direct admission of the extracted request. LoopFuzz is closed-loop: IPSM growth, state productivity, and hypothesis fitness determine when the LLM is queried, what context it receives, and whether its output is admitted.

The three loops in Fig.~\ref{fig:arch} define the analytical roles of the method. The Grammar Hypothesis Loop constructs and repairs message hypotheses from RFC knowledge, seed traces, and observed responses. The Fuzz Execution Loop performs state selection, mutation, bounded execution, IPSM update, and novelty checking. The LLM Intervention Loop is activated only under plateau conditions and returns either a validated continuation or a bounded control action.

\subsection{Grammar Hypothesis Loop}
Let $\mathcal{L}(c, s, \Sigma)$ denote the LLM generation function under prompt context $c$, state summary $s$, and protocol knowledge $\Sigma$. LoopFuzz uses $\mathcal{L}$ in two stages. At startup, it preserves ChatAFL's template extraction and seed enrichment path. It parallelizes enrichment so that initial corpus diversification does not dominate early campaign time. During fuzzing, it adds a lazily initialized hypothesis layer. This layer is activated at the first plateau event and updated through sampled validation and refinement. The separation is important. Startup enrichment broadens the initial seed set. Runtime hypotheses support runtime-validated control during long campaigns.

The Grammar Hypothesis Loop draws on three evidence sources: RFC fragments, queued seed traces or packet examples, and observed server responses, including response codes and error texts. For each message type $m$, the loop maintains a hypothesis $h_m=(G_m,\Phi_m)$. Here, $G_m$ is an ABNF-style or template-style production, and $\Phi_m$ is a set of field constraints. In LoopFuzz, $\Phi_m$ captures length bounds, enumerated values, token dependencies, and simple cross-field relations. This representation is more constrained than free-form text and lighter than a full formal protocol specification. We choose it because sampled online validation must remain cheap.

\subsection{Runtime Admission Controller}
The runtime admission controller is the central mechanism in our design. It does not formally prove correctness. Instead, it enforces four runtime checks before an LLM contribution can affect the campaign: parseability, acceptability, state reachability, and coverage gain. A candidate intervention $x$ is admitted only if
\[
A(x)=P(x) \land U(x) \land R(x) \land G(x),
\]
where $P$ denotes local parseability, $U$ denotes response-grounded acceptability, $R$ denotes evidence of new or redirected state reachability, and $G$ denotes downstream gain in IPSM structure or coverage.

\subsubsection{Structured Output and Parseability}
The plateau stage accepts either a concrete next-request candidate or a bounded structured-action object. Runtime validation first checks structural well-formedness, field types, length bounds, and action-schema consistency. LoopFuzz then tests local parseability against the current message hypotheses. It reuses parsed message regions already available during ordinary execution. The goal is simple: reject structurally invalid interventions before they perturb campaign control.

\subsubsection{Response-Grounded Acceptability}
Parseability alone is insufficient. A parsed request can still be semantically premature. LoopFuzz therefore classifies the resulting response and treats a non-rejection response as positive evidence. Rejected or persistently unproductive responses reduce state productivity and hypothesis fitness. This gives an execution-grounded notion of acceptability rather than a semantic proof. The verifier asks a narrow question: does live target behavior support admission?

\subsubsection{State Reachability and Coverage Gain}
The final admission question is whether a candidate helps the campaign. LoopFuzz measures this with the standard AFLNet-style novelty test on new IPSM states, new IPSM transitions, or new edge coverage. The verifier therefore uses a state-transition-tree-like signal derived from the IPSM, not text quality alone. A hypothesis fragment remains in active use only when execution provides positive evidence in state reachability or coverage. Fluent but repeatedly unproductive candidates are filtered out at the control boundary instead of accumulating as low-value queue bias.

\subsection{CEGR}
When sampled validation fails repeatedly, LoopFuzz records a concrete counterexample. The record contains the minimized request fragment, the observed response, and the mismatch against the current hypothesis. Refinement is deliberately local. Instead of rewriting the full protocol description, the method updates one field constraint or one production fragment at a time. This single-patch discipline narrows the model's search space, limits unconstrained edits, and makes the repair path auditable. The resulting update is reintegrated into protocol matching and re-evaluated by later sampled validation.

\subsection{State-Aware Scheduling and Plateau-Triggered Assistance}
Reducing malformed generations solves only half of the problem. Stateful fuzzers also stagnate when the campaign keeps revisiting locally dense IPSM regions while failing to cross narrow protocol bridges. LoopFuzz therefore treats IPSM feedback as a first-class scheduling signal.

To address this, LoopFuzz augments state selection with a frontier bonus $\beta$ derived from the out-degree of the IPSM:
\[
\beta = \begin{cases}
4.0 & \text{if } \deg^+(s) \le 1 \\
2.0 & \text{if } \deg^+(s) \le 3 \\
1.0 & \text{otherwise}
\end{cases}
\]
States not yet present in the IPSM receive the maximum bonus $\beta{=}4$. LoopFuzz then modulates this bonus with a three-level error-productivity hint (0=unknown, 1=likely-error, 2=confirmed-productive). This hint downweights frontier states that repeatedly behave like rejection sinks, but it does not discard them outright. In the current implementation, hint level 1 applies a $\beta{\times}0.5$ penalty. Hint level 0 is reduced to $\beta{\times}0.7$ only after repeated low-productivity selections ($\mathit{selected\_times}{\ge}30$ and $\mathit{productivity}{<}0.005$). Hint level 2 receives no penalty. The hint is initialized from response-code classification and updated online. As a result, states can be promoted or demoted as evidence accumulates rather than being fixed by an early response pattern. This policy approximates a rare-transition preference without requiring an exact model of the full protocol state space.

These constants should be read as the reported control policy, not as a claim of global optimality. The three frontier-bonus levels $\{4.0,2.0,1.0\}$ separate unseen or low-out-degree frontier states from denser regions by coarse preference rather than by fine-grained tuning. The error-productivity penalties and the $(30,0.005)$ gate were chosen to reduce repeated investment in response-derived rejection sinks while still allowing those states to recover if later executions become productive. Likewise, the $(80,30\%)$ node-stagnation safeguard and the 64-call intervention budget are bounded control parameters that prevent persistent hot-spot lock-in and unbounded LLM overhead. We report them to make the control policy auditable; this draft does not claim a full sensitivity analysis over the entire hyperparameter surface.

A complementary node-stagnation mechanism tracks whether IPSM growth has collapsed at the graph level rather than only at the local state level. When no new nodes appear for an extended interval, the scheduler intermittently injects random selection to avoid persistent hot-spot lock-in. In the reported configuration, that safeguard activates after 80 consecutive rounds without node growth and uses a 30\% random-selection probability.

Plateau detection uses the IPSM edge growth rate $\dot{E}$ (edges gained per minute), recalculated every 60 seconds of wall-clock time, to set an adaptive threshold:
\[
\tau(\dot{E}) = \begin{cases}
300 & \text{if } \dot{E} > 5 \\
200 & \text{if } 1 < \dot{E} \le 5 \\
150 & \text{if } \dot{E} \le 1
\end{cases}
\]
The initial value is $\tau{=}200$ for textual protocols; MQTT uses a higher adaptive floor in the current implementation and is reported separately in the evaluation. More generally, LoopFuzz treats plateau triggering as a rate-sensitive control decision, not as a fixed-frequency query rule. Assistance is invoked only when edge growth remains weak and the model-intervention budget is not exhausted. In the reported configuration, the plateau path opens when the unproductive streak reaches $\tau$ and prior model interventions remain below 64. Once inside that path, hypotheses are initialized lazily on first use. Refinement remains gated by validation count and accumulated counterexamples. Prompts are deduplicated over the most recent 64 LLM invocations. This prevents assistance from reacting to the same state summary again and again. For a novel prompt, the method builds a structured state summary from IPSM statistics, the least productive states, and seed identifiers, and then queries the model in an isolated subprocess. The model may return a concrete continuation toward an underexplored state or a bounded control action such as target-state redirection, seed reprioritization, or bounded mutation proposals. The result is admitted only after validation. In short, assistance is conditional, budgeted, and state-directed.

\begin{algorithm}[htbp]
\caption{Runtime-Validated Plateau Recovery in LoopFuzz}
\label{alg:fuzz}
\SetAlgoLined
\small
\KwIn{Target $T$, LLM function $\mathcal{L}$, Corpus $C$, Target edge growth $\dot{E}$}
\KwOut{Coverage bitmap $\mathcal{B}_{global}$, IPSM $\mathcal{M}$}
Initialize global bitmap $\mathcal{B}_{global} \leftarrow \emptyset$\;
Initialize IPSM $\mathcal{M} \leftarrow \emptyset$\;
\While{Campaign Time $<$ 24 hours}{
    $s \leftarrow \text{SelectSeed}(C, \mathcal{M})$\;
    $trace_{exec}, Q_{path} \leftarrow \text{MutateAndExecute}(T, s)$\;
    $\text{UpdateIPSM}(\mathcal{M}, Q_{path})$\;
    $\text{UpdateFrontierScores}(\mathcal{M})$\;
    \If{$\text{ShouldSampleValidate}()$}{
        $\text{ValidateHypothesesOnParsedRegions}(Q_{path})$\;
    }
    \If{$\text{PlateauDetected}(\tau(\dot{E}))$}{
        \If{$\text{HypCtxMissing}()$}{
            $\text{InitHypLazily}(C, Q_{path})$\;
        }
        \If{$\text{RefineGateOpen}()$}{
            $\text{CEGR\_RefineLowFitnessHyp}()$\;
        }
        $c_{state} \leftarrow \text{BuildStatePrompt}(\mathcal{M}, C, Q_{path})$\;
        \If{$\neg \text{PromptSeen\_Dedup}(c_{state})$}{
            $r \leftarrow \text{ForkQueryLLM}(\mathcal{L}, c_{state})$\;
            \If{$A(r) \equiv P(r) \land U(r) \land R(r) \land G(r)$}{
                $\text{ActionDispatch}(r, C)$\;
            }
        }
    }
}
\end{algorithm}

Algorithm~\ref{alg:fuzz} specifies the plateau path and the hypothesis-refinement gate. It formalizes how state-aware triggering, Runtime Verifier checks, and CEGR interact within one campaign loop.

This integration also imposes an execution discipline. Startup enrichment is parallelized so that LLM-based seed completion does not dominate early wall-clock time. Hypothesis construction is deferred until the first plateau event. This avoids paying the full refinement cost before the campaign exposes evidence of stagnation. LLM queries run in an isolated subprocess. Network-side cleanup is bounded to prevent persistent stalls on forking daemons. These mechanisms are not separate novelty claims. They are the conditions that keep runtime-validated intervention compatible with long-running stateful fuzzing.

\section{Experimental Evaluation Design}

We organize the evaluation around three research questions that match the paper's main claims. We ask whether closed-loop admission control changes whole-campaign behavior, whether the shipped state-aware control policy helps campaigns escape IPSM plateaus, and whether those effects persist in final 24-hour outcomes.
\begin{itemize}
    \item \textbf{RQ1 (Whole-Campaign Effect):} Does runtime-validated LLM assistance prevent the coverage regressions that can arise from direct open-loop generation?
    \item \textbf{RQ2 (IPSM Escape Dynamics):} Does the shipped state-aware control policy---including frontier-aware scheduling and plateau-triggered intervention---sustain IPSM growth after the baselines begin to stall?
    \item \textbf{RQ3 (End-of-Campaign Outcome):} Under equal 24-hour budgets, what is the effect of the shipped LoopFuzz control policy on final code-edge coverage and final IPSM-edge count relative to prior stateful greybox baselines?
\end{itemize}

\subsection{Experimental Setup}
We run all experiments on a dedicated Ubuntu 20.04 server with 32 CPU cores and 64GB RAM. The benchmark suite spans 10 implementations across seven protocol families:
\begin{enumerate}
    \item \textbf{FTP:} LightFTP, bftpd, ProFTPD, and Pure-FTPd.
    \item \textbf{SMTP:} Exim.
    \item \textbf{RTSP:} Live555.
    \item \textbf{SIP:} Kamailio.
    \item \textbf{DAAP/DACP:} Forked-daapd.
    \item \textbf{HTTP:} Lighttpd1.
    \item \textbf{MQTT:} Mosquitto.
\end{enumerate}

The benchmark suite contains 10 targets. The primary comparison now uses all nine off-the-shelf non-MQTT targets with complete repeated 24-hour summaries: LightFTP, bftpd, ProFTPD, Pure-FTPd, Exim, Live555, Kamailio, Forked-daapd, and Lighttpd1. Each primary system-target pair contributes 10 completed 24-hour runs. Mosquitto is kept in the paper as a supplemental matched-support case rather than being folded into the aggregate claim set.

Mosquitto requires a separate fairness note. Neither AFLNet nor ChatAFL originally shipped with MQTT support. We therefore implemented the MQTT response-code dissector and seed infrastructure for all three primary systems before running the matched-support comparison. We additionally reproduce MBFuzzer on Mosquitto and report that row as an auxiliary coverage-only baseline. Because the AFLNet/ChatAFL MQTT rows depend on author-added support and because MBFuzzer is a protocol-specialized competitor, we do not pool Mosquitto into the same aggregate claim as the nine off-the-shelf targets.

All evaluated subjects are textual or semi-textual request/response protocols. We restrict our claims to this regime. The method is not yet validated on opaque binary or encrypted protocols such as DNS, TLS, SSH, DTLS, or DICOM.

Both ChatAFL and LoopFuzz use the same pinned \texttt{GPT-4o-mini} endpoint. Prompts remain protocol-agnostic beyond protocol name, observed state, and runtime summary. We do not hand-specialize prompt text per target. Each campaign runs for 24 hours. The primary table uses only archived repeated runs from the single standardized results directory for each target, with no per-system cherry-picking of directories or best runs.

\subsection{Baselines, Metrics, and Statistical Protocol}
We use two baseline layers. The \emph{primary} baselines are AFLNet as the stateful greybox baseline and ChatAFL as the direct LLM-assisted baseline. These are the two systems with the closest implementation lineage to LoopFuzz, and all three run under the same hardware, target versions, and 24-hour budget. The \emph{auxiliary} reproduced baselines are NSFuzz on eight non-HTTP/non-MQTT targets and MBFuzzer on Mosquitto. We report those auxiliary comparisons only for final coverage because their archived outputs do not provide directly compatible IPSM summaries or identical logging semantics across all targets.

The main dependent variables for the primary comparison are end-of-campaign code-edge coverage and final IPSM-edge count. We treat code-edge coverage as the primary endpoint because it is the least system-specific measure among the available campaign summaries. We treat IPSM-edge count as a secondary diagnostic of state-exploration behavior rather than as a standalone efficacy claim, because it depends on a response-derived abstraction maintained within the fuzzing loop. For each primary target and metric, we summarize terminal values over 10 independent 24-hour runs with mean and sample SD and apply a two-sided exact Mann-Whitney U test to the per-run terminal values. We use the time-series plots to show campaign dynamics, not to claim significance at every timestamp. We also preserve crash artifacts, but this draft still does not claim novel vulnerabilities because crash triage and root-cause validation are not yet normalized across the suite. Importantly, the auxiliary NSFuzz and MBFuzzer artifacts expose different state abstractions; their reported \texttt{edges} or analogous state counts are therefore not directly commensurate with the primary IPSM-edge metric and are intentionally excluded from Table~\ref{tab:aux_results}.

\subsection{Code-Driven Ablation Design}
The current ablation design follows the shipped implementation rather than an idealized orthogonal factorization. The archived ablation matrix compares the shipped adaptive controller (\texttt{adaptive\_full}) against three bundled policy removals---\texttt{wo\_refinement}, \texttt{wo\_frontier}, and \texttt{wo\_state\_prompt}---plus two fixed-threshold controls, \texttt{fixed200\_full} and \texttt{fixed512\_full}. This organization matches the current code path: frontier weighting and error penalties share one switch; state-aware context and structured \texttt{actions[]} share one switch; and disabling adaptive triggering changes how often the plateau path, lazy hypothesis initialization, and Tier-2 refinement are reached at all.

These ablations should therefore be read as code-driven policy perturbations, not as clean per-module causal isolates. \texttt{wo\_refinement} disables Tier-2 local repair while Tier-1 sampled validation remains active. \texttt{wo\_frontier} removes both out-degree bonus and error-productivity penalty. \texttt{wo\_state\_prompt} falls back to the simple ChatAFL-style prompt and disables structured control actions. The fixed-threshold runs preserve the rest of the LoopFuzz controller but replace adaptive plateau updates with an explicit threshold. Some archived ablation directories contain corrupted or extra tarballs; for reproducibility we retain only runs with at least 1400 minutes of archived runtime and, when more than 10 valid runs remain, keep the lowest 10 run IDs.

\subsection{Trace Accounting and Cost Reporting}
Because LoopFuzz is a closed-loop LLM-in-the-loop system, the evaluation must report more than coverage alone. We therefore log each plateau event with its prompt, raw model reply, and token use. We also log each refinement event with the affected hypothesis and its counterexamples. These logs are sufficient to recover target-level admission statistics such as parseability pass rate, response-grounded acceptance rate, and CEGR repair outcomes, but those summaries are not yet normalized across the full archive and are therefore left out of the current draft. As a result, semantic drift remains a motivating failure mode and an auditable trace category here, not a quantified cross-target headline metric.

The archived cost logs cover 98 ChatAFL runs and 98 LoopFuzz runs across the 10-target suite; LightFTP and Pure-FTPd each miss two cost rows in the archive. Across those archived runs, ChatAFL averages 154.0 LLM calls, 36.9K prompt tokens, 95.9K completion tokens, and \$0.0631 per 24-hour campaign. LoopFuzz averages 185.9 LLM calls, 155.0K prompt tokens, 63.3K completion tokens, and \$0.0612 per 24-hour campaign. The mean dollar cost is therefore comparable overall, but the token mix shifts from completion-heavy free-form generation in ChatAFL to prompt-heavy structured control in LoopFuzz. Mean LoopFuzz cost ranges from \$0.0238 on Mosquitto to \$0.1762 on Live555.

\subsection{RQ1: Whole-Campaign Effect}
LoopFuzz is evaluated here as an integrated control policy, not as an isolated rejection heuristic. Table~\ref{tab:24h_results} shows that direct open-loop assistance is not uniformly robust under the current 10-run protocol: ChatAFL still finishes below AFLNet on Exim, Forked-daapd, and Lighttpd1, even though it helps on several FTP targets. Under these conditions, improved generation alone does not consistently translate into stronger end-of-campaign outcomes.

Across the nine off-the-shelf primary targets, LoopFuzz reaches the highest mean final code-edge coverage on all nine. Exact Mann-Whitney testing narrows the strongest same-target evidence to ProFTPD, Pure-FTPd, Exim, Forked-daapd, and Lighttpd1. LightFTP, bftpd, Live555, and Kamailio remain positive but descriptive. The Mosquitto matched-support row also favors LoopFuzz over AFLNet and ChatAFL. However, Table~\ref{tab:aux_results} shows that the broader baseline picture is mixed: LoopFuzz significantly exceeds NSFuzz on bftpd and ProFTPD, remains statistically tied on Kamailio, and trails NSFuzz on LightFTP, Pure-FTPd, Exim, Live555, and Forked-daapd; it also trails MBFuzzer on Mosquitto coverage. The robust claim supported by the data is therefore stronger than before but still bounded: LoopFuzz consistently improves over the closest AFLNet/ChatAFL lineage, not over every specialized external fuzzer.

\section{Discussion}

The paper makes one central claim. In stateful protocol fuzzing, LLM generation is useful only when it is governed by a strict admission boundary. ChatAFL already showed that an LLM can generate protocol text~\cite{chatafl}. LoopFuzz asks a different question: when should such output be trusted by the campaign? Our answer is closed-loop runtime admission control. It checks structure, parseability, response-grounded acceptability, state reachability, and downstream gain before an LLM suggestion can strengthen the queue. This changes the role of the LLM from queue producer to hypothesis proposer.

The admission controller and the scheduler solve different parts of the same problem. Admission control filters low-value suggestions. It does not decide where to spend the recovered budget. State-aware scheduling decides where to search. Without closed-loop intervention, however, it still depends on ordinary mutation to cross semantic bottlenecks. LoopFuzz combines the two because admission control and state-directed search reinforce each other.

The results also show why response-derived state counts must be read carefully. A campaign can accumulate superficially different rejection paths without moving toward high-value logic. LoopFuzz therefore reads IPSM exploration together with code-edge coverage and demotes states that remain unproductive over repeated selections. In this setting, productive states matter more than raw state counts. For that reason, IPSM-edge count is best interpreted as a companion diagnostic for campaign behavior, not as a substitute for code-edge coverage.

The present method is evaluated on textual or semi-textual protocols whose message regions can be parsed cheaply and whose responses reveal useful progress signals. That scope covers the benchmark suite used here and many request-response protocols of practical interest. Opaque binary or encrypted protocols require stronger parsers, auxiliary instrumentation, or richer response abstractions. Response codes alone may not expose state reachability in those settings. That extension matters, but it lies beyond the current empirical scope.

The present evaluation is also centered on campaign-control behavior rather than on vulnerability yield. We preserve crashes and queue artifacts, but we do not report new CVEs or newly confirmed bugs in this draft because crash deduplication, exploitability review, and cross-target triage are not yet complete under one uniform protocol. The paper should therefore be read as evidence about campaign control and exploration quality, not yet as an end-to-end demonstration of superior bug-finding yield.

Counterexample-guided local refinement is also a deliberate design choice. Repeated unconstrained regeneration does not accumulate persistent knowledge. Local refinement turns failed executions into stored evidence. It makes runtime evidence cumulative rather than disposable. At the same time, the ablation table shows that the exposed refinement switch is not uniformly decisive on every target. The novelty therefore lies in the control interface between model output and system execution, not in prompt wording alone.

\section{Threats to Validity}

\textbf{Internal validity:} LLM-assisted fuzzing remains sensitive to generation variance, target nondeterminism, and campaign-level timing effects. We mitigate these threats by fixing the execution environment, pinning the model endpoint, using low temperatures for grammar extraction and refinement, and designing the campaign matrix around repeated 24-hour runs. Even so, plateau triggering and hypothesis refinement are history-dependent. Early differences can propagate into late-campaign variance. The study also cannot cleanly separate model variance from control-policy variance because both act within the same long-running campaigns.

\textbf{External validity:} The benchmark suite spans 10 implementations across seven protocol families. Our strongest aggregate claims use the nine off-the-shelf non-MQTT targets in the primary AFLNet/ChatAFL/LoopFuzz comparison. The evidence is therefore strongest for textual or semi-textual protocols whose progress is visible in responses. We do not claim unchanged transfer to opaque binary or encrypted protocols without stronger format-specific adaptors. We now include direct auxiliary reproduced comparisons against NSFuzz on eight targets and MBFuzzer on Mosquitto, but those rows remain coverage-only and target-specific rather than a unified cross-system IPSM comparison.

\textbf{Construct and reproducibility validity:} We use code-edge coverage and final IPSM-edge count as the main proxies for fuzzing effectiveness. These are standard SGF measurements, but neither fully captures semantic protocol progress. Our closed-loop runtime admission boundary refers to structured output checks, sampled hypothesis checks, response-grounded acceptability, state-reachability signals, and counterexample-guided refinement. It does not mean formal verification or a perfect pre-execution oracle. We also do not yet report cross-target admission summaries such as parseability pass rate, response-grounded acceptance rate, or CEGR repair success rate, so the motivating semantic-drift narrative is operationalized through logs rather than reduced to one global prevalence number. We reduce fairness ambiguity where possible. ChatAFL and LoopFuzz share the same pinned model endpoint. Each primary target is drawn from one completed standardized results directory with 10 archived runs. Mosquitto is compared only after matched MQTT support was added to every primary system, so that row still warrants more cautious interpretation than the off-the-shelf targets. The ablation table is likewise a faithful but imperfect archive-level reconstruction because some ablation directories contain corrupted or extra tarballs; we therefore publish and use a deterministic run-selection rule instead of hand-picking replacements.

\section{Conclusion}
Fluent protocol text is insufficient for a stateful campaign. What matters is a closed-loop runtime admission boundary that can reject semantically premature generations and refine them when they fail.

Under the primary 10-run comparison against AFLNet and ChatAFL, LoopFuzz is more robust than direct open-loop LLM assistance. On the nine off-the-shelf targets, it achieves the highest mean final code-edge coverage and the highest mean final IPSM-edge count on every target; the strongest same-target code-edge evidence appears on ProFTPD, Pure-FTPd, Exim, Forked-daapd, and Lighttpd1, while IPSM-edge gains are strongest on LightFTP, bftpd, ProFTPD, Pure-FTPd, Exim, Live555, and Kamailio. A matched-support Mosquitto case follows the same direction versus AFLNet and ChatAFL. At the same time, the broader baseline picture is mixed: NSFuzz remains stronger on final coverage for five of the eight targets where we reproduced it, MBFuzzer remains stronger on Mosquitto coverage, and the archived ablations do not support a claim that every exposed LoopFuzz sub-control is individually necessary across all targets. The evidence therefore supports a precise conclusion: closed-loop runtime admission control is a stronger campaign-control policy than direct open-loop LLM insertion within the closest AFLNet/ChatAFL lineage, but this draft does not establish universal superiority over specialized external fuzzers.
