ChatAFL（基线）与 ChatAFL-Opt 的工作流、本质与底层逻辑
一、ChatAFL 基线的完整工作流
第一阶段：初始化

程序启动后，主函数依次完成命令行参数解析、共享内存和 fork server 的初始化、IPSM（推断协议状态机）的创建，以及初始种子队列的导入。在这个阶段，LLM 相关的设置非常简单：仅从环境变量中读取 API Key，不做任何协议知识的预加载，也不初始化任何假设模型或状态上下文结构。config.h 中定义了两个关键常量：UNINTERESTING_THRESHOLD 设为 512，CHATTING_THRESHOLD 设为 64。前者表示当某个种子在连续 512 次变异中都没有发现新路径或新状态时，才认为该种子进入了"停滞"状态；后者表示当连续 64 次模糊测试周期都没有全局性的新发现时，才触发一次 LLM 对话。

第二阶段：种子选择与状态评分

在主循环的每一轮中，模糊测试器首先需要从队列中选出一个种子进行变异。选择依据是每个种子的"得分"，得分计算公式是固定的：score = ceil(1000 × 2^(log(选中次数)) × 2^(log(语料库中属于该状态的种子数)))。这个公式的含义是：一个状态被选中的次数越多、该状态拥有的种子数越多，其得分就越高——而在实际调度逻辑中，低分种子优先，因此这个公式倾向于把机会给那些"较少被探索"和"种子较少"的状态。关键问题在于：这个公式完全不考虑状态在 IPSM 图上的拓扑位置。一个已经被充分探索、出度很高的中心节点和一个刚刚发现、只有一条出边的边界节点，在其他条件相同时获得完全相同的调度优先级。

第三阶段：变异与执行

选定种子后，模糊测试器对其进行比特翻转、算术运算、字典替换、拼接等标准 AFL 变异操作。每次变异后，通过 send_over_network 函数将变异后的数据包序列发送给目标服务器，然后通过共享内存读取覆盖率位图，通过 IPSM 状态机记录协议状态转移。send_over_network 函数内部有两个关键的 while(1) 循环：第一个循环在发送完所有数据包后反复检查覆盖率位图是否稳定，只要发现新的覆盖位就继续等待；第二个循环在检测到子进程退出后反复检查进程是否真正终止。这两个循环都没有设置上限，意味着如果目标服务器响应异常缓慢或者进程卡住，模糊测试器会无限期地阻塞在这里。一旦 send_over_network 决定终止子进程，它发送 SIGKILL 信号，但在 Fix-14a 之前的版本中，SIGKILL 导致的非正常退出会被误判为 FAULT_CRASH，污染崩溃统计数据。

第四阶段：停滞检测与 LLM 介入

当某个种子的连续无新发现次数（region_count_num）超过 UNINTERESTING_THRESHOLD（512 次）时，该种子被标记为"不感兴趣"。当全局性的连续无新发现轮次超过 CHATTING_THRESHOLD（64 次）时，触发 LLM 对话。触发后的流程是：调用 construct_prompt_stall 函数，该函数使用简单的文本模板，拼接当前目标协议名称和已知的消息类型列表，生成一段纯文字提示词，大意是"我在测试 X 协议的服务器，已知以下消息类型，当前测试停滞了，请建议新的消息序列"。这段提示词不包含任何关于当前 IPSM 拓扑的信息——不知道有多少状态、哪些状态之间有转移、哪些状态是边界——LLM 完全是在"盲猜"。

提示词构造完成后，直接在主进程中调用 chat_with_llm 函数发起 HTTP 请求。这意味着在等待 LLM 响应期间（通常需要数秒到数十秒），整个模糊测试主循环完全暂停，不进行任何变异和执行。LLM 返回的响应是自由格式的文本，使用正则表达式提取其中的消息序列。提取过程简单且脆弱：用正则匹配类似"COMMAND arg1 arg2"的模式，如果 LLM 的回复格式略有偏差，提取就可能失败或提取到错误内容。提取到的消息序列被加入种子队列，然后主循环恢复。

第五阶段：协议文法充实

除了停滞时的 LLM 介入外，ChatAFL 还有一个"enrichment"机制：当发现新的协议消息类型时，调用 LLM 询问该消息类型的语法结构，以便生成更精确的变异。这个充实过程是串行的、阻塞式的——每发现一个新消息类型就发起一次 LLM 请求，主循环在此期间完全停止。如果一次性发现了多个新消息类型，则需要依次等待多次 LLM 响应，累积的停顿时间可能非常显著。

本质总结：

ChatAFL 的 LLM 集成本质上是一个"定时触发的盲目翻译器"。它不观察模糊测试的实际状态，只看一个简单的计数器是否超过固定阈值；它不分析 IPSM 的拓扑结构，只知道有哪些消息类型；它不区分状态的探索价值，对所有状态一视同仁；它在主进程中同步调用 LLM，阻塞整个模糊循环；它用正则表达式解析自由文本，容易丢失或误解 LLM 的建议。用控制论的术语说，这是一个开环控制器：输入是固定的阈值触发信号，输出是未经验证的文本建议，中间没有任何反馈回路。

二、ChatAFL-Opt 的完整工作流
第一阶段：初始化（延迟加载设计）

程序启动时，同样完成参数解析、共享内存、fork server 和 IPSM 的初始化。但与基线不同，Opt 在此阶段初始化了一系列额外的全局变量：child_force_killed 标志位（用于 Fix-14a 的 SIGKILL 误报修正）、last_edges_count 和 edges_growth_rate（用于自适应阈值计算）、adaptive_plateau_threshold（初始值 100）、以及假设系统的全局句柄指针（初始值 NULL）。关键的设计决策是"延迟初始化"：grammar-hypothesis、rfc-knowledge、hypothesis-adapter 等重量级模块不在启动时加载，而是推迟到第一次 LLM 交互时才初始化。这样做的好处是避免在模糊测试的前期探索阶段（此时新发现频繁，不需要 LLM 帮助）浪费资源。config.h 中 UNINTERESTING_THRESHOLD 设为 100（而非 512），但实际运行中这个值会被自适应机制动态覆盖。

第二阶段：种子选择与前沿加权

Opt 的种子评分公式在基线的基础上增加了一个"前沿加权因子"（frontier bonus）。评分过程首先计算基线的基础得分，然后查询当前种子所属状态在 IPSM 图中的出度（out_degree），即从该状态出发有多少条已知的状态转移边。如果出度小于等于 1，说明这个状态几乎没有被探索，是真正的"前沿"，得分乘以 4 倍加权（实际效果是大幅提高被选中概率）。如果出度在 2 到 3 之间，得分乘以 2 倍。如果出度大于等于 4，说明该状态已经连接了较多的转移路径，不再给予额外加权。这个机制的底层逻辑是：在协议模糊测试中，状态空间的边界（低出度节点）最有可能隐藏未发现的转移和代码路径，应该被优先探索。这解释了为什么实验数据中 Opt 的边覆盖率提升如此显著（10 个目标全部获胜，平均提升 50.5%）——前沿加权直接引导模糊测试器去发现新的状态转移边。

第三阶段：变异与执行（有界循环 + SIGKILL 修正）

变异操作本身与基线相同，但 send_over_network 函数内部的两个 while(1) 循环被改造为有界循环。覆盖率稳定性等待循环设置了 500 次迭代上限，每次循环间隔约 1 毫秒，总等待不超过 500 毫秒。进程终止确认循环改为：发送 SIGKILL 后等待 50 毫秒，若进程仍未退出则跳出循环。这消除了主循环因异常服务器响应而无限阻塞的风险。同时，Fix-14a 的修正确保：当 child_force_killed 标志被设置（即进程是被 SIGKILL 强制终止的），即使 waitpid 返回的状态表明异常退出，也将结果标记为 FAULT_NONE 而非 FAULT_CRASH，避免污染崩溃统计。

第四阶段：自适应停滞检测

Opt 不使用固定的停滞阈值，而是每 60 秒（实际实现中是每经过一定的模糊测试周期）重新计算一次 adaptive_plateau_threshold。计算依据是"边增长率"（edges_growth_rate），即过去 60 秒内新发现的 IPSM 边数。计算逻辑如下：如果边增长率大于 5（即每分钟发现超过 5 条新状态转移），说明探索势头良好，将阈值上调到 150，减少不必要的 LLM 干预以免打断高效的自主探索。如果边增长率在 1 到 5 之间，说明探索速度中等，阈值保持 100。如果边增长率小于等于 1（即基本停滞），将阈值下调到 50，加快 LLM 介入速度。这个机制的底层逻辑是：LLM 调用有较高的时间成本（网络延迟 + 推理时间），在探索顺畅时应该让模糊测试器自主运行，只在真正需要帮助时才请求 LLM 指导。用控制论术语说，这是一个基于系统输出（边增长率）的自适应反馈机制。

第五阶段：状态感知的 LLM 介入

当停滞条件满足后，Opt 的 LLM 介入流程与基线有根本性差异。

首先是延迟初始化检查：如果假设系统（grammar-hypothesis）尚未初始化，在此时完成初始化，包括加载 RFC 知识库和创建假设适配器。

然后是状态上下文构造：调用专门的函数遍历整个 IPSM 图，为每个状态收集以下信息——状态编号、该状态在当前模糊测试会话中被命中的次数、该状态下发现的唯一路径数、该状态的出度、到达该状态所经过的消息序列。这些信息被组织成一个结构化的 JSON 对象（state_ctx），各状态按"探索效率"（唯一路径数除以命中次数）排序，效率最低的排在前面，提示 LLM 重点关注这些"瓶颈"状态。

提示词构造使用 json-c 库构建结构化的 JSON 消息，而非手工拼接字符串。提示词的内容远比基线丰富：包含协议名称、当前 IPSM 的节点总数和边总数、上述排序后的状态详细信息、以及明确的指令——要求 LLM 以两种策略之一回复：策略 A 是 suggested_request（建议一个具体的消息序列来探索某个低效率状态），策略 B 是 actions 数组（包含三种结构化操作：set_target_state 指定下一步应优先探索的目标状态、prioritize_seeds 提升某些种子的优先级、propose_mutations 建议对特定字节偏移进行特定变异）。temperature 参数设为 1.2（基线未显式设置），鼓励 LLM 产生更多样化的建议。

LLM 调用使用 fork 隔离：主进程 fork 一个子进程来执行 HTTP 请求，主进程通过管道读取结果。如果子进程在 150 秒内没有返回，主进程杀掉子进程并继续运行。这意味着即使 LLM 服务出现超时或故障，模糊测试主循环最多阻塞 150 秒而不会无限挂起。实际实现中，这段等待时间内主进程也会进行一些轻量级的后台处理。

响应解析使用 llm-validator 模块进行严格的 JSON 模式验证。验证器检查返回的 JSON 是否包含预期的字段名和类型，拒绝不合规的响应。通过验证后，按照操作类型分别处理：set_target_state 操作修改 IPSM 的状态选择权重；prioritize_seeds 操作调整种子队列中指定种子的优先级；propose_mutations 操作将建议的变异点和变异值记录下来，在下一轮变异中优先应用。如果 LLM 返回的是 suggested_request（一个完整的消息序列），则直接将其转换为种子加入队列。

第六阶段：并行协议文法充实

Opt 将文法充实过程从串行改为并行。具体实现是使用 pthread 线程池：当发现多个新消息类型时，为每个消息类型创建一个独立的线程，各线程并行地向 LLM 发起请求。三阶段流水线设计为：第一阶段，主线程收集所有待充实的消息类型；第二阶段，线程池并行执行所有 LLM 请求；第三阶段，主线程汇总所有响应并更新文法知识库。这大幅减少了充实过程对主循环的阻塞时间——如果有 5 个新消息类型需要充实，基线需要 5 倍的串行等待时间，而 Opt 只需要约 1 倍（取决于线程池大小和 LLM 服务的并发能力）。

第七阶段：节点停滞检测

Opt 还实现了一个额外的"节点停滞"机制：如果某个状态连续 80 轮被选中但都没有产生新发现，模糊测试器将以 30% 的概率随机选择其他状态进行探索，打破"热点锁定"——即避免模糊测试器过度集中于某个看似有潜力但实际已枯竭的状态。

三、两者的本质区别与底层逻辑
基线的本质是"被动触发的文本翻译器"。 它的工作模式是：等待一个固定计数器超过固定阈值，然后向 LLM 发送一段不含任何运行时状态信息的文本提示，从 LLM 返回的自由文本中用正则表达式抽取消息序列，加入种子队列。整个过程中，LLM 不知道模糊测试器当前在哪个状态、哪些状态已被充分探索、哪些状态是边界；模糊测试器也不根据 LLM 的响应质量调整后续的提问策略。这是一个没有反馈的单向信息流。

Opt 的本质是"自适应的状态感知协作器"。 它的工作模式是：持续监控边增长率，动态调整 LLM 介入时机；在触发时，将完整的 IPSM 拓扑信息（状态数、边数、每个状态的探索效率、到达路径）编码为结构化 JSON 传递给 LLM；要求 LLM 返回结构化操作指令而非自由文本；用严格的 JSON 验证器校验响应；将 LLM 的建议转化为三种具体的控制动作（目标状态重定向、种子优先级调整、精确变异点建议）。整个过程形成一个闭环：模糊测试器的运行时状态流入 LLM，LLM 的结构化建议流回模糊测试器并影响其后续行为，而行为的结果又通过下一次的状态上下文反馈给 LLM。

用控制论的框架来理解：

ChatAFL 基线是一个开环控制系统。控制信号（LLM 建议）的生成不依赖于系统的实际输出（覆盖率、状态转移）。阈值是预设的常数，提示词是固定模板，响应解析是脆弱的正则匹配。系统无法自我纠正——如果 LLM 给出了低质量的建议，基线无从知晓，下次停滞时仍然会发送同样模板的提示词。

ChatAFL-Opt 是一个自适应闭环控制系统。它有三个可观测量：边增长率（宏观探索速度）、IPSM 拓扑（微观状态结构）、每状态探索效率（局部饱和度）。它有三个执行器：状态选择权重（控制"去哪里"）、种子优先级（控制"用什么"）、变异建议（控制"改哪里"）。控制律是自适应的：阈值 τ(t) 根据边增长率 Ė 动态调整（Ė>5 → τ=150, 1<Ė≤5 → τ=100, Ė≤1 → τ=50）；前沿加权因子 β 根据出度动态调整（deg⁺≤1 → β=4, deg⁺≤3 → β=2, deg⁺≥4 → β=1）。

这种架构差异导致了实验中观察到的所有性能差异：

边覆盖率全面碾压（10 个目标全胜，平均加 50.5%），根本原因是前沿加权机制将探索资源集中到低出度的边界状态，这些状态正是新转移边最可能被发现的位置。

节点覆盖率中等提升（6 胜 4 平，平均加 7.8%），因为新节点的发现本身就是小概率事件，但状态感知的 LLM 建议能针对性地建议触达未知状态的消息序列，比盲猜更有效。

代码覆盖率稳步提升（分支覆盖 7 胜，行覆盖 8 胜），因为更多的状态转移意味着更多的协议逻辑分支被执行。

初始发现速度显著加快，因为自适应阈值在早期探索放缓时（Ė≤1）迅速将阈值降到 50，比基线的固定 512 快十倍触发 LLM 介入。

吞吐量不受损（部分目标甚至提升），因为并行充实和 fork 隔离的 LLM 调用大幅减少了主循环的阻塞时间，有界循环消除了异常阻塞风险。
