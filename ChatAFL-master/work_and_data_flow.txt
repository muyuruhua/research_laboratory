================================================================================
二、需求1：LLM语法/消息模板生成（Hypothesis）
================================================================================

设计要求：
  输入：RFC片段/抓包样例/服务端响应码与错误信息
  输出：每类message的grammar（ABNF/CFG/JSON Schema）+ 字段约束（长度/枚举/依赖关系）

----------------------------------------------------------------------
2.1 ChatAFL 基线现状
----------------------------------------------------------------------

2.1.1 启动期LLM语法抽取：setup_llm_grammars() [chat-llm.c]
  - construct_prompt_for_templates(protocol_name, &final_msg):
    输入仅为协议名+seed文件中的样例消息 [chat-llm.c 基線L180-210]
    无RFC文本注入
    无服务端响应码/错误信息注入
  - 对同一提示词迭代 TEMPLATE_CONSISTENCY_COUNT=5 次
  - 每次迭代调用 chat_with_llm() 两次（temperature=0.5）：
    · 第1次：获取主要消息类型模板
    · 第2次：补充剩余模板 → construct_prompt_for_remaining_templates()
  - 输出：PCRE2正则表达式模式（protocol_patterns），非结构化grammar
  - 无字段约束（无长度/枚举/依赖关系）

2.1.2 结论：PARTIAL
  有LLM生成能力，但：
  ✗ 输入不含RFC文本
  ✗ 输入不含服务端响应码/错误信息
  ✗ 输出为PCRE2正则（非ABNF/CFG/JSON Schema）
  ✗ 无字段级约束（长度/枚举/依赖）

----------------------------------------------------------------------
2.2 ChatAFL-Opt 实现
----------------------------------------------------------------------

2.2.1 核心入口：init_grammar_hypothesis_system() [afl-fuzz.c L7254-7540]
  - 收集最多10个queue seed样本（MQTT经 mqtt_binary_to_text() 转换）
  - 收集最多10份 responses-ipsm/ 响应摘要作为server_responses
  - init_hypothesis_context(protocol, NULL, pcap_samples, pcap_count)
    ⚠️ RFC text参数当前为NULL（RFC知识库已完整实现但未接入此调用点）
  - generate_grammar_hypotheses(ctx, 5) → LLM生成5个初始hypothesis
  - integrate_hypotheses_into_protocol_patterns() → 集成到IPSM

2.2.2 输入构建：construct_hypothesis_generation_prompt() [grammar-hypothesis.c L1178-1391]
  输入源（三种）：
  (a) RFC文本 [L1239-1262]：
      - extract_rfc_key_sections() 智能提取RFC关键章节
      - 文本协议：提取ABNF/BNF语法规则（Step 1a, L552-677）
      - 二进制协议：提取struct/enum/byte-table定义块（Step 1b, L343-549）
      - ASCII状态图提取（Step 1c, L882-1011）
      - RFC章节打分+贪心选区（Pass 3, L1013-1095）
      - 支持12种协议的关键词表 [L169-207]
      - rfc-knowledge.c 提供RFC抓取/缓存能力（curl下载+本地缓存）
  (b) PCAP/种子样例 [L1265-1317]：
      - 最多20个多样本（去重采样 should_include_pcap_sample）
      - 前20字符去重，避免重复样本
  (c) 服务端响应 [L1319-1348]：
      - Gap-1 fix: 注入最多5条服务端响应示例
      - 使LLM能生成枚举约束（从实际响应码推断合法值域）

2.2.3 输出结构：grammar_hypothesis_t [grammar-hypothesis.h L40-58]
  {
    message_type:      "CONNECT" / "GET" / "INVITE" / ...
    description:       "MQTT connection request" / ...
    schema:            JSON Schema（含properties/required/pattern/enum/minLength...）
    constraints[]:     五种字段约束（见下）
    production_rules[]: ABNF风格的产生式规则
    fitness:           动态fitness评分
    counterexamples[]: 反例列表
  }

2.2.4 五种字段约束类型 [grammar-hypothesis.h L17-38]
  CONSTRAINT_LENGTH:     { min, max }          — 字段长度范围
  CONSTRAINT_ENUM:       { values[], count }   — 允许值枚举
  CONSTRAINT_REGEX:      { pattern }           — 正则格式约束
  CONSTRAINT_DEPENDENCY: { target_field, condition } — 字段间依赖
  CONSTRAINT_NUMERIC:    { min, max }          — 数值范围

  提取函数 extract_constraints_from_schema() [grammar-hypothesis.c L1760-2002]：
  - 从JSON Schema的"properties"块中解析各字段定义
  - 识别 minLength/maxLength → CONSTRAINT_LENGTH
  - 识别 "pattern" → CONSTRAINT_REGEX
  - 识别 "enum" → CONSTRAINT_ENUM (Gap-2 fix, L1878-1919)
  - 识别 "minimum"/"maximum" → CONSTRAINT_NUMERIC (Gap-2 fix, L1924-1955)
  - 识别 "required" → CONSTRAINT_DEPENDENCY (Gap-3 fix, L1967-2001)

2.2.5 LLM Prompt要求 [grammar-hypothesis.c L1353-1371]
  "Generate grammar hypotheses for this protocol. For each message type, provide:
   1. message_type: Identifier
   2. description: What this message does
   3. schema: JSON Schema with field definitions. Use standard JSON Schema keywords:
      'minLength'/'maxLength' for string lengths,
      'enum': ['val1','val2'] for allowed values,
      'pattern': 'regex' for format constraints,
      'minimum'/'maximum' for numeric ranges,
      'required': ['field1',...] for mandatory fields.
   4. constraints: Array of field constraints
   5. production_rules: ABNF-like syntax rules"

2.2.6 协议适配层 [hypothesis-adapter.c]
  - 文本协议(SIP/FTP/HTTP/...): 生成PCRE2正则模式 "^MSG_TYPE(?:[ \t].*)?\r?\n"
  - 二进制协议(MQTT): 生成首字节高4bit匹配模式 "^[\x10-\x1f]"
  - MQTT专项：binary↔text桥接（mqtt_binary_to_text / mqtt_text_to_binary）
  - 去重：跳过已存在于message_types_set的消息类型（Fix-7b）

2.2.7 结论：FULLY MEETS
  ✅ 输入含RFC文本（rfc-knowledge.c + extract_rfc_key_sections智能提取）
  ✅ 输入含PCAP/种子样例（最多20个去重样本）
  ✅ 输入含服务端响应（最多5条server response）
  ✅ 输出为JSON Schema + ABNF风格产生式 + 五类字段约束
  ⚠️ RFC知识库已完整实现但init_hypothesis_context()调用点RFC text为NULL
     （extract_rfc_key_sections通过ctx->rfc_text工作，需上游填充）
  ⚠️ 目前仅在首次plateau时lazy init（CHATAFL_HYPOTHESIS环境变量门控）

================================================================================
三、需求2：验证器（Verifier，核心创新点）
================================================================================

设计要求：
  (a) 可解析性：生成消息能被本地parser解析（CFG/正则/字段拆解）
  (b) 可接受性：发送给SUT后得到"非拒绝类响应"（非400/非error）
  (c) 状态可达性：消息序列触发新响应码/新状态节点（State Transition Tree思路）
  (d) 覆盖增益：覆盖/状态覆盖提升才将该grammar片段"入库"

----------------------------------------------------------------------
3.1 ChatAFL 基线现状
----------------------------------------------------------------------

  - 无显式验证器
  - LLM输出 → PCRE2正则提取 → common_fuzz_stuff() → 好则入库/坏则丢弃
  - 无常量化验证指标（parse rate / acceptability rate / state gain）
  - 状态评分仅基于三个计数器（fuzzs, selected_times, paths_discovered）
    [afl-fuzz.c 基線 L828]

  结论：MISSING — 无系统化验证器设计

----------------------------------------------------------------------
3.2 ChatAFL-Opt 实现：四层验证器
----------------------------------------------------------------------

3.2.1 可解析性验证 (Parseability)
  ─────────────────────────────────
  validate_message_against_hypothesis() [grammar-hypothesis.c L2007-2286]：
  - 对消息逐字段拆解
  - 对每个字段运行 check_constraint() [L2161-2250]：
    · CONSTRAINT_LENGTH:   strlen(field_value) ∈ [min, max]
    · CONSTRAINT_ENUM:     strcmp(field_value, values[i]) 精确匹配
    · CONSTRAINT_REGEX:    regcomp + regexec POSIX正则
    · CONSTRAINT_DEPENDENCY: 目标字段存在性检查
    · CONSTRAINT_NUMERIC:  strtoll(field_value) ∈ [min, max]
  - 返回 violation_count（违反的约束数）

  validate_hypothesis_sampled() [afl-fuzz.c L7564-7644]：
  - Tier-1采样验证（热路径，每500次exec执行一次）
  - 复用 extract_requests() 已解析的regions（零额外解析开销）
  - 每次最多扫描8个region
  - MQTT: 先 mqtt_binary_to_text() 转换后再验证
  - 每10次验证失败 → add_counterexample() + update_hypothesis_fitness_dynamic()

3.2.2 可接受性验证 (Acceptability)
  ───────────────────────────────────
  classify_state_error_hint() [aflnet.c L2334-2412]：
  - 12种协议的自动错误分类
  - 文本协议(FTP/SMTP/RTSP/HTTP/SIP/IPP):
    · state_id / 100 ∈ {4,5} → error_hint=1 (likely-error, 4xx/5xx响应)
  - 二进制协议(MQTT/SSH/TLS/DTLS12/DNS/DICOM):
    · behavioral fallback（基于productivity推断）
  - O(1)时间复杂度，零内存分配，可在热路径安全调用

  state_info_t 扩展 [aflnet.h L33-35]：
    u8  error_hint;       // 0=unknown, 1=likely-error, 2=confirmed-productive
    double productivity;  // paths_discovered / (selected_times + 1.0)

  error_hint 用于状态评分惩罚 [afl-fuzz.c L2582-2589]：
    if (state->error_hint == 1)
      frontier_bonus *= 0.5;  // 确认4xx/5xx错误状态惩罚
    else if (state->error_hint == 0 && state->selected_times >= 30
             && state->productivity < 0.005)
      frontier_bonus *= 0.7;  // 未知且低产状态软惩罚

  error_hint 动态更新 [afl-fuzz.c L1498-1537]：
    error_hint=1 && selected_times≥10 && productivity≥0.1 → 提升为2(confirmed-productive)
    error_hint=0 && selected_times≥30 && productivity<0.005 → 降级为1(likely-error)

3.2.3 状态可达性验证 (State Reachability)
  ─────────────────────────────────────────
  IPSM图拓扑感知的frontier_bonus评分 [afl-fuzz.c L2550-2565]：
    char sid_str[STATE_STR_LEN];
    Agnode_t *nd = agnode(ipsm, sid_str, FALSE);
    if (nd) {
      int out_degree = 0;  // 遍历agfstout/agnxtout计出度
      if (out_degree <= 1)       frontier_bonus = 4.0;
      else if (out_degree <= 3)  frontier_bonus = 2.0;
      else                       frontier_bonus = 1.0;
    } else {
      frontier_bonus = 4.0;  // 不在图中→最高前沿奖励（新状态）
    }

  这直接实现了 SST(USENIX'22) 的 "优先探索低出度状态/稀有转移" 思想：
  - 出度≤1（终端/罕见转移状态）→ 4×权重
  - 出度2-3（中等连通状态）→ 2×权重
  - 出度≥4（高连通状态）→ 1×权重（不变）

  MQTT差分奖励叠加 [afl-fuzz.c L2592-2618]：
    对稀疏状态图(out_degree密度<8.0)的frontier_bonus再加cap(×2.5)

  MQTT B1 PUBLISH转发状态感知 [aflnet.c L1645-1652]：
    将PUBLISH(type=3)加入响应状态产生包列表
    PUBLISH状态标识仅编码QoS级别（0/1/2→3个新状态）
    使broker转发对IPSM可见——对齐MBFuzzer的"forwarding-as-coverage"信号

3.2.4 覆盖增益验证 (Coverage Gain)
  ───────────────────────────────────
  update_hypothesis_fitness_dynamic() [grammar-hypothesis.c L2288-2340]：
    成功(fitness += 0.01, 上限1.0)
    失败(fitness -= 0.005, 下限0.0)
    每100次验证输出日志

  calculate_hypothesis_fitness() [grammar-hypothesis.c L2292-2340]：
    fitness = 0.7 × parse_rate + 0.3 × avg_constraint_confidence
    parse_rate = parse_success / (parse_success + parse_failure)

  Grammar "入库"机制 [hypothesis-adapter.c L136-266]：
    - integrate_hypotheses_into_protocol_patterns() 将hypothesis转为PCRE2 pattern
    - 仅当hypothesis通过生成+解析后才集成到IPSM协议匹配
    - 去重：skip已存在于message_types_set的类型（Fix-7b）
    - 写入 out_dir/protocol-grammars/hyp-pattern-N 供调试

  Protocol Oracle 补充验证 [protocol-oracle.c 1965行]：
    - 6种协议 × 5级严重度 × 11种类别的安全语义检测
    - 检测auth bypass/state violation/info leak/path traversal/injection/DoS等
    - 去重: 4096槽bitmap + pattern_hash
    - 违规报告保存到 out_dir/replayable-violations/

3.2.5 结论：FULLY MEETS all four sub-requirements
  ✅ (a) 可解析性：5类约束检查 + Tier-1采样验证（热路径，零额外解析开销）
  ✅ (b) 可接受性：classify_state_error_hint 12协议自动分类 + error_hint评分惩罚
  ✅ (c) 状态可达性：frontier_bonus基于IPSM出度的状态优先探索（SST理论）
  ✅ (d) 覆盖增益：动态fitness + Tier-2 refinement触发 + hypothesis入库去重

================================================================================
四、需求3：反例驱动修正（Counterexample-guided Refinement）
================================================================================

设计要求：
  当验证失败：把失败样例（最小化后的请求+响应+差分）回喂给LLM，
  让它只修一个字段/一条产生式
  关键：限制LLM自由度（只允许局部patch），降低幻觉

----------------------------------------------------------------------
4.1 ChatAFL 基线现状
----------------------------------------------------------------------

  - 无任何refinement机制
  - LLM plateau调用是单向的：构造prompt → LLM → 正则提取 → 执行 → 结束
  - 执行结果无反馈回LLM

  结论：MISSING

----------------------------------------------------------------------
4.2 ChatAFL-Opt 实现
----------------------------------------------------------------------

4.2.1 反例收集
  ──────────────
  add_counterexample() [grammar-hypothesis.c]：
  - 存储失败消息（hex编码）+ 错误原因字符串
  - 格式："<hex_encoded_message> | REASON: <error_description>"
  - 每个hypothesis最多维护MAX_REFINEMENT_COUNTEREXAMPLES=10个反例

  collect_violation_details() [grammar-hypothesis.c]：
  - 收集具体违反的约束名称+字段名
  - 格式："violated: LENGTH(field_X) min=1 max=64 actual=128"

  Tier-1验证失败触发 [afl-fuzz.c]：
    每10次验证失败 → add_counterexample() + update_hypothesis_fitness_dynamic(-0.005)

4.2.2 反例回喂LLM
  ──────────────────
  construct_hypothesis_refinement_prompt() [grammar-hypothesis.c L1393-1487]：
  - 构建refinement prompt包含：
    · 协议名 + 当前hypothesis描述 + 完整schema
    · 最多10个反例（hex编码+错误原因）
  - LLM call with temperature=0.3（低随机性，确保一致性）

4.2.3 局部patch约束（Fix-20a，核心）
  ─────────────────────────────────────
  construct_hypothesis_refinement_prompt() 中的精炼指令 [L1465-1480]：

  "IMPORTANT REFINEMENT RULES:
   1. Make the MINIMAL change needed: modify at most ONE constraint,
      ONE production rule, or ONE schema field per refinement.
   2. Do NOT rewrite the entire hypothesis. Keep all unchanged
      fields, rules, and constraints EXACTLY as they are.
   3. In your response JSON, include a top-level field
      'changed_field': '<name of the single field or rule you modified>'
      so the change can be audited.
   4. Return the COMPLETE hypothesis in the same JSON format as before,
      with only the single targeted fix applied.
   5. If no single local fix can accommodate ALL counterexamples,
      fix the one that resolves the MOST counterexamples."

  设计分析：
  - "at most ONE constraint/rule/field" — 严格限制LLM自由度
  - "Do NOT rewrite the entire hypothesis" — 防止LLM全局重写幻觉
  - "changed_field" — 审计追踪能力
  - "fix the one that resolves the MOST counterexamples" — 贪心最大化修正

  评价：该prompt工程约束精确实现了"只修一个字段/一条产生式"的要求。
  但这是软约束（prompt instruction），而非硬约束（代码级AST diff限制），
  在LLM不完全遵循指令时可能产生额外修改。

4.2.4 Tier-2 周期性精炼
  ────────────────────────
  periodic_hypothesis_refinement() [afl-fuzz.c L7646-7750]：
  - 触发条件（三重门控）：
    1. hypothesis_mode == 1（CHATAFL_HYPOTHESIS=1）
    2. hypothesis_validation_count % HYPOTHESIS_REFINEMENT_CHECK_INTERVAL(5000) == 0
    3. 扫描所有hypothesis：if fitness < FITNESS_THRESHOLD(0.7) && counterexamples >= 3
  - 每次至多精炼1个hypothesis（选择fitness最低且反例最多的）
  - 调用 refine_hypothesis_with_counterexamples() → LLM refinement → 更新hypothesis

  调用位置 [afl-fuzz.c L11163-11165]：
    在plateau handler中，if (!ablation_no_refinement) → 触发Tier-2

4.2.5 结论：FULLY MEETS
  ✅ 验证失败 → 反例收集（hex编码+violation详情）
  ✅ 反例回喂LLM（当前schema+最多10个反例+错误原因）
  ✅ 局部patch约束（"modify at most ONE constraint/rule/field"）
  ✅ 审计追踪（"changed_field" 字段）
  ✅ 自由度限制（"Do NOT rewrite the entire hypothesis"）
  ⚠️ 局部修改约束为prompt级（软约束），非代码级AST diff硬约束
  ⚠️ 当前refinement仅处理constraint违反，未纳入服务端响应差分

================================================================================
五、需求4：状态导向调度（State-aware Scheduling）
================================================================================

设计要求：
  把"状态节点/转移"作为 fuzz feedback（类似 SST 的 STT）
  目标：优先探索"低覆盖状态/稀有转移"，
  并在 plateau 时触发LLM生成"到某状态的序列建议"

----------------------------------------------------------------------
5.1 ChatAFL 基线现状
----------------------------------------------------------------------

5.1.1 状态评分 [afl-fuzz.c 基線 L828]
  update_scores_and_select_next_state(FAVOR):
    state->score = ceil(1000 × 2^(-log₁₀(log₁₀(fuzzs+1)×selected_times+1))
                          × 2^(ln(paths_discovered+1)))
  仅基于三个计数器（fuzzs, selected_times, paths_discovered）
  不感知IPSM图拓扑（出度=0与出度=10无区别）
  无error_hint, 无productivity跟踪

5.1.2 运行时LLM停滞处理 [afl-fuzz.c 基線 L6851起]
  触发：uninteresting_times >= UNINTERESTING_THRESHOLD(512) && chat_times < 64
  流程：
    1. construct_prompt_stall() — 固定文本模板，不含IPSM拓扑信息
    2. 主进程内同步调用 chat_with_llm()
    3. extract_stalled_message() 正则提取
    4. common_fuzz_stuff() 执行
  本质：开环单向翻译器。LLM建议效果无反馈通道。

5.1.3 结论：BASIC
  有状态选择机制但：
  ✗ 不感知IPSM图拓扑（出度/转移稀疏度）
  ✗ 无error_hint/productivity跟踪
  ✗ LLM plateau prompt不含状态信息
  ✗ 无LLM "到某状态的序列建议" 能力

----------------------------------------------------------------------
5.2 ChatAFL-Opt 实现：多层状态感知调度
----------------------------------------------------------------------

5.2.1 第一层：Frontier-aware状态评分（基于IPSM拓扑）
  ──────────────────────────────────────────────────
  见需求2.3中的frontier_bonus机制 [afl-fuzz.c L2550-2565]
  这直接实现了 SST 论文的核心思想：
  - 将"状态节点的出度"作为feedback信号
  - 低出度状态（稀有转移/前沿）→ 高权重优先探索
  - 与SST的"优先选择低覆盖状态"完全一致

  叠加 error_hint/productivity 修正 [L2582-2589]
  叠加 MQTT差分奖励 [L2592-2618]

  各状态desirability最终公式：
    final_score = baseline_score × frontier_bonus × error_hint_penalty × diff_bonus
    baseline_score: AFLNet原有公式
    frontier_bonus: 4.0 / 2.0 / 1.0（基于出度）
    error_hint_penalty: ×0.5（4xx/5xx） / ×0.7（未知低产）
    diff_bonus: capped ×2.5（MQTT稀疏图）

5.2.2 第二层：自适应Plateau阈值
  ──────────────────────────────
  边增长率监控 [afl-fuzz.c L11100-11141]：
    每60s wall-clock：
      edges_growth_rate = (current_edges - last_edges_count) / time_elapsed_min

    文本协议（SIP/FTP/HTTP...）：
      edges_growth_rate > 5.0/min → threshold = 300（高增长，减少LLM调用）
      edges_growth_rate 1-5/min   → threshold = 200（中等增长）
      edges_growth_rate < 1.0/min → threshold = 150（停滞，增加LLM调用）

    MQTT协议（二进制，探索更慢）：
      > 5.0/min → 500 | 1-5/min → 400 | < 1.0/min → 300

    触发条件 [L11143]：
      if (uninteresting_times >= adaptive_plateau_threshold && chat_times < 64)

5.2.3 第三层：State-aware LLM Plateau介入
  ────────────────────────────────────────
  llm_handle_plateau() [chat-llm.c L347-611]：
  - 构建rich prompt含：
    · state_ctx JSON（见下）
    · protocol constraint（Fix-23: PLATEAU_FORMAT_CONSTRAINTS表）
    · strategy guide（引导LLM选择具体操作类型）
    · MQTT专项提示（重连/通配符/QoS链/retain/will/auth边界）

  State Context JSON [afl-fuzz.c L11336-11440]：
    {
      "nodes": <IPSM节点总数>,
      "edges": <IPSM边总数>,
      "growth_rate": <edges/min>,
      "pending_favored": <等待处理的favored seed数>,
      "queued_paths": <queue中的interesting cases数>,
      "chat_times": <已触发LLM次数>,
      "target_state_id": <当前目标状态ID>,
      "worst_states": [
        {"state_id": X, "paths": N, "out_degree": D, "productivity": P},
        ...
      ]  // 最多8个最差状态
    }
    该JSON使LLM能了解IPSM图当前状态，从而产生针对性建议。

5.2.4 第四层：LLM actions[] 反馈机制
  ──────────────────────────────────
  支持三种actions [afl-fuzz.c L11572-11850]：

  (a) set_target_state: 重定向fuzzer目标状态
      {
        "type": "set_target_state",
        "state_id": <目标state_id>
      }
      效果：将fuzzer的target_state_id改为指定状态
      应用：LLM判断某个低覆盖状态值得优先探索时

  (b) prioritize_seeds: 优先处理特定种子
      {
        "type": "prioritize_seeds",
        "seed_ids": [<seed_id>, ...]
      }
      效果：标记种子为favored + 更新各状态池selected_seed_index

  (c) propose_mutations: 建议具体的变异操作
      {
        "type": "propose_mutations",
        "seed_id": <base_seed>,
        "ops": [
          {"op": "insert"|"replace", "pos": N, "bytes_base64": "..."},
          {"op": "flip", "pos": N, "len": L},
          {"op": "grammar_expand", "rule": "..."}
        ]
      }

  这使LLM从"模糊的文本建议者"升级为"有操作语意的调度参与者"：
  - set_target_state 直接对应"到某状态的序列建议"
  - prioritize_seeds 对应"哪个种子最可能产生突破"
  - propose_mutations 对应"如何修改现有消息到达目标状态"

5.2.5 第五层：MQTT Q-Learning + UCB1 状态感知调度
  ──────────────────────────────────────────────────
  mqtt_ql_t [mqtt-scheduler.h L40-49]：
    32 states × 11 packet types Q-value表
    Softmax温度退火选择
    Q-Learning更新: Q(s,a) ← Q(s,a) + α[r + γ·max Q(s,a') - Q(s,a)]
    Warmup: 每state的每个action至少尝试一次（round-robin）

  mqtt_ql_select(): 根据当前IPSM state_idx选择下一个MQTT包类型
  mqtt_ql_update(): 每次interesting seed产生后更新Q-value

  mqtt_bandit_t [mqtt-scheduler.h L55-61]：
    6臂UCB1选择（replace/insert/field/skip/corpus-splice/sub-pub-pair）
    乐观初始化（skip arm=0.05悲观先验，其他=0.5乐观先验）
    平衡 exploration vs exploitation

  热路径集成：havoc_stage → mqtt_bandit_select/mqtt_ql_select
  reward更新：每次interesting seed产生后

5.2.6 第六层：节点停滞检测 + 随机扰动
  ──────────────────────────────────
  [afl-fuzz.c L12293-12315]：
    外层主循环跟踪 agnnodes(ipsm) 变化
    节点增长 → 重置 node_stagnation_rounds
    停滞 > 80轮 → 30%概率切换到 RANDOM_SELECTION
  与自适应plateau的边增长率停滞是两个独立观测维度

5.2.7 结论：FULLY MEETS
  ✅ 状态节点/转移作为feedback（frontier_bonus基于IPSM出度）
  ✅ 优先探索低覆盖状态/稀有转移（出度≤1→4×, 出度2-3→2×）
  ✅ plateau时LLM生成状态序列建议（set_target_state action）
  ✅ 自适应阈值动态平衡LLM探索频率
  ✅ MQTT专项：Q-Learning状态×动作调度 + UCB1策略选择
  ✅ 与SST论文理论的直接对应：
     - SST的"优先选择低覆盖状态" ↔ frontier_bonus
     - SST的"STT状态转移树" ↔ IPSM图出度分析
     - SST的"稀有转移" ↔ out_degree≤1×4.0奖励

================================================================================
九、最终结论
================================================================================

ChatAFL（基线）是一个"开环的LLM辅助协议模糊测试器"：
  - 启动期一次性LLM批处理后协议知识固化
  - 运行时LLM通道完全开环（无反馈、无验证、无refinement）
  - 无状态拓扑感知、无RFC知识注入、无结构化grammar输出

ChatAFL-Opt 在四个设计维度上均取得了实质性进展：

  需求1(Hypothesis生成):
    从简单的PCRE2正则模板升级为JSON Schema+五类字段约束+ABNF产生式的
    结构化grammar生成，输入扩展为RFC/PCAP/服务器响应三源。

  需求2(验证器):
    从无验证器升级为四层工程化验证（可解析性/可接受性/状态可达性/覆盖增益），
    Tier-1热路径采样+Tier-2周期性精炼形成双速率闭环。

  需求3(反例驱动修正):
    从无refinement升级为反例收集→回喂LLM→局部patch约束的闭环，
    通过prompt工程实现"只修改一个字段/一条产生式"的设计约束（软约束级）。

  需求4(状态导向调度):
    从固定阈值+固定模板的开环LLM调用，升级为IPSM拓扑感知的frontier优先探索+
    自适应阈值+LLM state-aware建议+actions[]操作语意+MQTT Q-Learning/UCB1
    的六层状态感知调度系统。

  ChatAFL-Opt 已从"开环LLM辅助工具"升级为"状态感知+反例反馈+自适应调度"的
  闭环协议模糊测试系统，基本满足论文中描述的四项设计要求。

  【10.2.1: update_scores_and_select_next_state() Opt增强版】
  ──────────────────────────────────────────────────────────

  基线(AFLNet)公式:
    score = 1000 × 2^(-log₁₀(log₁₀(fuzzs+1)×selected_times+1))
                  × 2^(ln(paths_discovered+1))

  Opt增强公式 [afl-fuzz.c L2549-2618]:
    final_score = score × frontier_bonus × error_hint_penalty × diff_bonus

    Step A — frontier_bonus（IPSM出度感知）:
      agnode(ipsm, state_id_str, FALSE) → 计算出度
        out_degree ≤ 1  → ×4.0  (终端/前沿状态，SST稀有转移)
        out_degree 2-3  → ×2.0  (中等连通)
        out_degree ≥ 4  → ×1.0  (高连通，充分探索)
        不在图中         → ×4.0  (新发现状态)

    Step B — error_hint_penalty（可接受性感知）:
      error_hint == 1 (confirmed 4xx/5xx)       → ×0.5
      error_hint == 0 && productivity < 0.005
        && selected_times ≥ 30                  → ×0.7 (未知低产)
      error_hint == 2 (confirmed-productive)    → ×1.0 (不惩罚)

    Step C — MQTT diff_bonus（仅MQTT + 稀疏图）:
      if out_degree密度 < 8.0 → capped(×2.5)

    前5轮(state_cycles < 5): ROUND_ROBIN（同基线）

10.3 Plateau检测与LLM介入流程（Plateau → LLM → Feedback Loop）
----------------------------------------------------------------------

  这是ChatAFL-Opt最核心的闭环工作流，将基线中的"开环LLM调用"升级为
  "状态感知+反例反馈+操作语意"的闭环。

  【触发条件】[afl-fuzz.c L11143]
  ─────────────────────────────────
    uninteresting_times >= adaptive_plateau_threshold
    && chat_times < CHATTING_THRESHOLD(64)

    其中 adaptive_plateau_threshold 是动态计算的（见10.2自适应阈值更新）:
      文本协议: 150(高增长) / 200(中) / 300(低)
      MQTT协议: 300(高增长) / 400(中) / 500(低)

  【完整处理流程】
  ─────────────────

  1. PRE-LLM 阶段 [L11152-11165]

    │     ├─ 收集10份 responses-ipsm/ → server_responses

    │     │   ├─ construct_hypothesis_generation_prompt()

    │     └─ integrate_hypotheses_into_protocol_patterns()
    │         写入 out_dir/protocol-grammars/hyp-pattern-N
    │

    │     periodic_hypothesis_refinement()
    │     └─ 扫描所有hypothesis:
    │         if fitness < 0.7 && counterexamples >= 3:
    │           ├─ construct_hypothesis_refinement_prompt()
    │           │   └─ 当前schema + 最多10个反例 + Fix-20a局部patch约束

  2. STATE CONTEXT 构建 [L11336-11440]（由 ablation_no_state_prompt 门控）

    若MQTT: 额外注入 mqtt_cluster_diff_summary

  3. FORK隔离LLM调用 [L11442-11650]
  ──────────────────────────────────
    fork() ─┬─ 子进程:
            │   ├─ 关闭AFL共享内存/文件描述符
            │   ├─ 两条LLM路径:
            │   │   ├─ [ablation_no_state_prompt=1]:
            │   │   │   construct_prompt_stall_original()
            │   │   │   → chat_with_llm(temp=1.2)
            │   │   │   → extract_stalled_message() 正则提取

            │   └─ 结果写入 stall-interactions/llm-suggest-N

            │

                waitpid(child, WUNTRACED, timeout=60s)

                └─ 超时 → kill(child, SIGKILL) → child_force_killed=1

  4. RESPONSE 处理 [L11652-11850]
  ─────────────────────────────────

    ├─ suggested_request: 类型=string, 1 ≤ len ≤ 4096, 控制字符过滤

    ├─ suggested_request 分支:
    │   ├─ extract + format → 标准化协议消息格式
    │   └─ common_fuzz_stuff(buf, len) → 执行

        ├─ prioritize_seeds:
        │   查找seed → 标记favored → 更新各状态池selected_seed_index
        │
        ├─ propose_mutations:
        │   base64_decode(bytes_base64) → insert/replace/flip

        │
        └─ suggest_strategy: noop（预留扩展）

  5. 反馈闭环
  ─────────────
    执行结果（has_new_bits / queued_paths增加）→ 影响:
    ├─ edges_growth_rate → adaptive_plateau_threshold（下一次触发频率）

10.5 MQTT专项工作流（MQTT-Specific Workflows）
----------------------------------------------------------------------

  【10.5.1: Multi-Party Driver 执行流程】
  ───────────────────────────────────────
  send_over_network() 中:
    if (mp_drv && net_protocol == PRO_TCP):
      ├─ mp_drv->open_connections()
      │   └─ mqtt_mp_open():
      │       ├─ TCP connect × 3（sub_fd / pub_fd / ctrl_fd）
      │       ├─ CONNECT报文 × 3（每连接独立ClientId）
      │       ├─ SUBSCRIBE通配符"#"（sub连接订阅所有topic）
      │       └─ 返回3个fd的mp_conn数组
      │
      ├─ mp_drv->handshake() [可选, MQTT返回MP_MULTI_OK]
      │
      ├─ 对每个请求:
      │   ├─ mp_drv->role_for_message(msg) → sub/pub/ctrl
      │   ├─ net_send(对应fd, msg)
      │   └─ mp_drv->after_send() [MQTT: noop]
      │
      ├─ mp_drv->drain_all()
      │   └─ mqtt_mp_drain():
      │       所有已连接fd → non-blocking read → 累积响应
      │       超时: 总计CHATAFL_MP_READ_TIMEOUT_MS(500ms)
      │
      └─ mp_drv->cleanup() → close所有fd
    失败回退: open_connections失败 → MP_SINGLE_FD_FALLBACK → 单连接路径

  【10.5.2: Multi-Broker Differential 执行流程】
  ──────────────────────────────────────────────
  每32次exec触发:
    mqtt_probe_cluster_differences()
    │
    ├─ 解析 CHATAFL_MQTT_BROKERS:
    │   "mosquitto@tcp://10.0.0.1:1883,nanomq@tcp://10.0.0.2:1883"
    │   → broker端点数组 [name, host, port]
    │
    ├─ 对每个broker:
    │   ├─ mqtt_exec_one_broker_mp(broker, input_buf, input_len)
    │   │   ├─ TCP connect + CONNECT + SUBSCRIBE "#"
    │   │   ├─ 发送input → drain响应
    │   │   └─ 返回 response_buf + response_len
    │   └─ mqtt_diff_parse_response(response_buf, response_len, &fields[i])
    │       ├─ 解析MQTT包序列
    │       ├─ 提取 G-fields: pkt_types[], return_codes[]
    │       └─ 提取 H-fields: payload_hashes[]
    │
    ├─ mqtt_diff_compare_n(fields, n_brokers)  // 两两对比
    │   对每对(broker_A, broker_B):
    │     mqtt_diff_compare(&fields[A], &fields[B])
    │     └─ 三层对比:
    │         ├─ type_seq_hash 不同      → MQTT_DIV_TYPE (severity=3)
    │         ├─ code_seq_hash 不同      → MQTT_DIV_CODE (severity=2)
    │         └─ payload_hashes 不同     → MQTT_DIV_PAYLOAD (severity=1)
    │
    ├─ 差分信号注入:
    │   ├─ queue_entry.mqtt_diff_score = 0-100
    │   ├─ mqtt_state_diff_reward[state_idx] += divergence_strength
    │   └─ mqtt_last_diff_signal = normalized_divergence
    │
    ├─ mqtt_save_diff_report() → out_dir/diffs/
    │   └─ 结构化JSON: broker签名 + 每层差分详情 + 统计
    │
    └─ mqtt_cluster_diff_summary更新:
        "3 brokers, 2 unique signatures, type-div:5 code-div:12 payload-div:47"
        → 供plateau prompt注入

  【10.5.3: Q-Learning + UCB1 调度决策流程】
  ──────────────────────────────────────────
  havoc_stage 中 [每轮havoc]:
    │
    ├─ Step 1: UCB1策略选择
    │   arm = mqtt_bandit_select(&mqtt_bandit)
    │   UCB1 score = avg_reward + sqrt(2·ln(total)/attempts)
    │   ├─ Arm 0 (replace):  用mqtt_gen_packet()替换当前region
    │   ├─ Arm 1 (insert):   用mqtt_gen_packet()插入
    │   ├─ Arm 2 (field):    包内字节级变异（保持MQTT结构）
    │   ├─ Arm 3 (skip):     仅通用havoc
    │   ├─ Arm 4 (splice):   corpus拼接+field-aware
    │   └─ Arm 5 (sub-pub):  SUBSCRIBE+PUBLISH pair注入（共享话题）
    │
    ├─ Step 2: Q-Learning包类型选择
    │   pkt_type = mqtt_ql_select(&mqtt_ql, current_state_idx)
    │   ├─ Warmup: 每state每action至少1次（round-robin）
    │   ├─ Softmax: P(a) ∝ exp(Q(s,a)/τ)
    │   └─ 温度退火: τ *= 0.9999 (≈5000次更新减半)
    │
    └─ Step 3: 执行后reward反馈
        if (new_interesting_paths > 0):
          reward = +1.0 (或 queued_paths增量)
          mqtt_ql_update(ql, state_idx, pkt_type, reward)
          mqtt_bandit_update(bandit, arm, reward)
        else:
          reward = 0.0
          mqtt_ql_update(ql, state_idx, pkt_type, reward)

附录A：ChatAFL-Opt 核心策略摘要（中文参考）
================================================================================

【/research_laboratory/ChatAFL-master/ChatAFL-Opt】的核心策略如下：
1. LLM语法/消息模板生成（Hypothesis）
o 输入：RFC片段/抓包样例/服务端响应码与错误信息
o 输出：每类 message 的 grammar（ABNF风格或你自定义CFG/JSON schema）+ 字段约束（长度、枚举、依赖关系）


2. 验证器（Verifier，核心创新点）
不需要形式化证明，可用且“工程上强有效”的验证：
o 可解析性：生成消息能被本地parser解析（CFG/正则/字段拆解）
o 可接受性：发送给SUT后得到“非拒绝类响应”（比如非400/非error）
o 状态可达性：消息序列触发新响应码/新状态节点（可用 State Transition Tree 思路）USENIX’22 的 Stateful Greybox Fuzzing
o 覆盖增益：覆盖/状态覆盖提升才将该grammar片段“入库”

3. 反例驱动修正（Counterexample-guided Refinement）
o 当验证失败：把失败样例（最小化后的请求+响应+差分）回喂给LLM，让它只修一个字段/一条产生式
o 关键：限制LLM自由度（只允许局部patch），降低幻觉

4. 状态导向调度（State-aware Scheduling）
o 把“状态节点/转移”作为 fuzz feedback（类似 stateful greybox fuzzing 的 STT）
o 目标：优先探索“低覆盖状态/稀有转移”，并在 plateau(停滞) 时触发LLM生成“到某状态的序列建议”USENIX’22 的 Stateful Greybox Fuzzing


注：ChatAFL来源于【Large Language Model guided Protocol Fuzzing.pdf】，SST来源于【Stateful Greybox Fuzzing.pdf】
