ChatAFL（基线）与 ChatAFL-Opt 的工作流、本质与底层逻辑
一、ChatAFL 基线的完整工作流
第一阶段：初始化

程序启动后，主函数依次完成命令行参数解析、共享内存和 fork server 的初始化、IPSM（推断协议状态机）的创建，以及初始种子队列的导入。在这个阶段，LLM 相关的设置非常简单：仅从环境变量中读取 API Key，不做任何协议知识的预加载，也不初始化任何假设模型或状态上下文结构。config.h 中定义了两个关键常量：UNINTERESTING_THRESHOLD 设为 512，CHATTING_THRESHOLD 设为 64。前者是 LLM 的实际触发阈值：当全局连续无新发现的执行次数（uninteresting_times）达到 512 时满足触发条件；后者是 LLM 调用总次数的上限——条件检查为 `chat_times < CHATTING_THRESHOLD`，即最多触发 64 次 LLM 调用，达到上限后即使继续停滞也不再请求 LLM。两者共同构成触发条件：`uninteresting_times >= 512 && chat_times < 64`。

第二阶段：种子选择与状态评分

在主循环的每一轮中，模糊测试器首先需要从队列中选出一个种子进行变异。选择依据是每个状态的"得分"，通过加权随机（得分越高被选中概率越大）选出目标状态。得分计算公式是固定的：score = ceil(1000 × 2^(-log₁₀(log₁₀(fuzzs+1) × selected_times + 1)) × 2^(ln(paths_discovered+1)))。第一个因子的指数为负，意味着一个状态的模糊测试次数（fuzzs）和被选中次数（selected_times）越多，该因子越小，得分越低；第二个因子使用自然对数，意味着该状态发现的新路径数（paths_discovered）越多，得分越高。综合效果是：这个公式倾向于把机会给那些"较少被探索"但"已有发现潜力"的状态——探索不足的状态得分高是因为惩罚因子小，而有过新发现的状态得分高是因为奖励因子大。关键问题在于：这个公式完全不考虑状态在 IPSM 图上的拓扑位置。一个已经被充分探索、出度很高的中心节点和一个刚刚发现、只有一条出边的边界节点，在其他条件相同时获得完全相同的调度优先级。

第三阶段：变异与执行

选定种子后，模糊测试器对其进行比特翻转、算术运算、字典替换、拼接等标准 AFL 变异操作。每次变异后，通过 send_over_network 函数将变异后的数据包序列发送给目标服务器，然后通过共享内存读取覆盖率位图，通过 IPSM 状态机记录协议状态转移。send_over_network 函数内部有两个关键的 while(1) 循环：第一个循环在发送完所有数据包后反复检查覆盖率位图是否稳定，只要发现新的覆盖位就继续等待；第二个循环在检测到子进程退出后反复检查进程是否真正终止。这两个循环都没有设置上限，意味着如果目标服务器响应异常缓慢或者进程卡住，模糊测试器会无限期地阻塞在这里。一旦 send_over_network 决定终止子进程，它发送 SIGKILL 信号，但在 Fix-14a 之前的版本中，SIGKILL 导致的非正常退出会被误判为 FAULT_CRASH，污染崩溃统计数据。

第四阶段：停滞检测与 LLM 介入

当全局连续无新发现的执行次数（uninteresting_times）超过 UNINTERESTING_THRESHOLD（512 次）且尚未达到调用上限（chat_times < CHATTING_THRESHOLD = 64）时，触发一次 LLM 对话。uninteresting_times 是一个全局计数器：每次 common_fuzz_stuff() 执行后，若 save_if_interesting() 返回真（发现新路径/新状态）则重置为 0，否则递增；触发后也立即重置为 0。因此它度量的是"全局最近连续多少次执行没有任何新发现"，而非某个特定种子的计数。触发后的流程是：调用 construct_prompt_stall 函数，该函数使用简单的文本模板，拼接当前目标协议名称和已知的消息类型列表，生成一段纯文字提示词，大意是"我在测试 X 协议的服务器，已知以下消息类型，当前测试停滞了，请建议新的消息序列"。这段提示词不包含任何关于当前 IPSM 拓扑的信息——不知道有多少状态、哪些状态之间有转移、哪些状态是边界——LLM 完全是在"盲猜"。

提示词构造完成后，直接在主进程中调用 chat_with_llm 函数发起 HTTP 请求。这意味着在等待 LLM 响应期间（通常需要数秒到数十秒），整个模糊测试主循环完全暂停，不进行任何变异和执行。LLM 返回的响应是自由格式的文本，使用正则表达式提取其中的消息序列。提取过程简单且脆弱：用正则匹配类似"COMMAND arg1 arg2"的模式，如果 LLM 的回复格式略有偏差，提取就可能失败或提取到错误内容。提取到的消息序列被加入种子队列，然后主循环恢复。

第五阶段：协议文法充实

除了停滞时的 LLM 介入外，ChatAFL 还有一个"enrichment"机制：当发现新的协议消息类型时，调用 LLM 询问该消息类型的语法结构，以便生成更精确的变异。这个充实过程是串行的、阻塞式的——每发现一个新消息类型就发起一次 LLM 请求，主循环在此期间完全停止。如果一次性发现了多个新消息类型，则需要依次等待多次 LLM 响应，累积的停顿时间可能非常显著。

本质总结：

ChatAFL 的 LLM 集成本质上是一个"定时触发的盲目翻译器"。它不观察模糊测试的实际状态，只看一个简单的计数器是否超过固定阈值；它不分析 IPSM 的拓扑结构，只知道有哪些消息类型；它不区分状态的探索价值，对所有状态一视同仁；它在主进程中同步调用 LLM，阻塞整个模糊循环；它用正则表达式解析自由文本，容易丢失或误解 LLM 的建议。用控制论的术语说，这是一个开环控制器：输入是固定的阈值触发信号，输出是未经验证的文本建议，中间没有任何反馈回路。

二、ChatAFL-Opt 的完整工作流
第一阶段：初始化（延迟加载设计）

程序启动时，同样完成参数解析、共享内存、fork server 和 IPSM 的初始化。但与基线不同，Opt 在此阶段初始化了一系列额外的全局变量：child_force_killed 标志位（用于 Fix-14a 的 SIGKILL 误报修正）、last_edges_count 和 edges_growth_rate（用于自适应阈值计算）、adaptive_plateau_threshold（初始值 100）、以及假设系统的全局句柄指针（初始值 NULL）。关键的设计决策是"延迟初始化"：grammar-hypothesis、rfc-knowledge、hypothesis-adapter 等重量级模块不在启动时加载，而是推迟到第一次 LLM 交互时才初始化。这样做的好处是避免在模糊测试的前期探索阶段（此时新发现频繁，不需要 LLM 帮助）浪费资源。config.h 中 UNINTERESTING_THRESHOLD 设为 100（而非 512），但实际运行中这个值会被自适应机制动态覆盖。

第二阶段：种子选择与前沿加权

Opt 的种子评分公式在基线的基础上增加了一个"前沿加权因子"（frontier bonus）。评分过程首先计算基线的基础得分，然后查询当前种子所属状态在 IPSM 图中的出度（out_degree），即从该状态出发有多少条已知的状态转移边。如果出度小于等于 1，说明这个状态几乎没有被探索，是真正的"前沿"，得分乘以 4 倍加权（实际效果是大幅提高被选中概率）。如果出度在 2 到 3 之间，得分乘以 2 倍。如果出度大于等于 4，说明该状态已经连接了较多的转移路径，不再给予额外加权。如果状态尚未出现在 IPSM 图中（全新节点），直接给予最高 4 倍加权。这是 Fix-5（前沿探索）的核心逻辑。

Fix-19（可接受性惩罚）在出度加权的基础上对错误响应状态进行进一步修正，分三层处理：

  • error_hint=1（结构性错误状态，服务器返回 4xx/5xx，尚未证明有探索价值）：frontier_bonus × 0.25，将最高 4.0 倍压至 1.0，避免错误死端垄断调度资源。

  • error_hint=0（响应类型未知，如 MQTT 等二进制协议）且行为性无效（该状态已被选中 ≥ 20 次但 productivity < 0.01）：frontier_bonus × 0.5，施加较温和的数据驱动惩罚。

  • error_hint=2（尽管返回错误码但已确认具有探索价值）：不施加任何惩罚，保留完整加权。

最终得分 = base × frontier_bonus（应用所有修正后的乘积）。这个机制的底层逻辑是：在协议模糊测试中，状态空间的边界（低出度节点）最有可能隐藏未发现的转移和代码路径，应该被优先探索，但已知的错误死端不应占用过多资源。这解释了为什么实验数据中 Opt 的边覆盖率提升如此显著（10 个目标全部获胜，平均提升 50.5%）——前沿加权直接引导模糊测试器去发现新的状态转移边。

第三阶段：变异与执行（有界循环 + SIGKILL 修正）

变异操作本身与基线相同，但 send_over_network 函数内部的两个 while(1) 循环被改造为有界循环。覆盖率稳定性等待循环设置了 500 次迭代上限，循环体内无延时调用（busy-loop 检查 has_new_bits），在典型硬件上总耗时约 25–50 毫秒。进程终止确认循环改为：先发送 SIGTERM，然后每 200 微秒轮询一次进程状态，最多等待 50 毫秒（250 次轮询 × 200µs）；若进程在 50 毫秒内仍未退出，则升级为 SIGKILL 强制终止。这消除了主循环因异常服务器响应而无限阻塞的风险。同时，Fix-14a 的修正确保：当 child_force_killed 标志被设置（即进程是被 SIGKILL 强制终止的），即使 waitpid 返回的状态表明异常退出，也将结果标记为 FAULT_NONE 而非 FAULT_CRASH，避免污染崩溃统计。

第四阶段：自适应停滞检测

Opt 不使用固定的停滞阈值，而是每 60 秒（wall-clock 时间，由 `cur_ms - last_edges_check_time >= 60000` 触发）重新计算一次 adaptive_plateau_threshold。计算依据是"边增长率"（edges_growth_rate），即过去 60 秒内新发现的 IPSM 边数。计算逻辑如下：如果边增长率大于 5（即每分钟发现超过 5 条新状态转移），说明探索势头良好，将阈值上调到 150，减少不必要的 LLM 干预以免打断高效的自主探索。如果边增长率在 1 到 5 之间，说明探索速度中等，阈值保持 100。如果边增长率小于等于 1（即基本停滞），将阈值下调到 50，加快 LLM 介入速度。这个机制的底层逻辑是：LLM 调用有较高的时间成本（网络延迟 + 推理时间），在探索顺畅时应该让模糊测试器自主运行，只在真正需要帮助时才请求 LLM 指导。用控制论术语说，这是一个基于系统输出（边增长率）的自适应反馈机制。

第五阶段：状态感知的 LLM 介入

当停滞条件满足后，Opt 的 LLM 介入流程与基线有根本性差异。

首先是延迟初始化检查：如果假设系统（grammar-hypothesis）尚未初始化，在此时完成初始化，包括加载 RFC 知识库和创建假设适配器。

然后是状态上下文构造：在 IPSM 图上为每个状态收集以下字段并编码为 JSON——状态编号（id）、关联路径总数（paths）、已发现的唯一新路径数（paths_discovered）、被选中次数（selected_times）、变异执行次数（fuzzs）、种子池大小（seeds_count）、是否为错误状态（is_error，取自 Fix-19 的 error_hint 字段）、生产率（productivity）、以及从该状态可达的最多 5 个种子索引（seed_ids）。state_ctx 对象还包含全局字段：当前 IPSM 节点数/边数、边增长率（growth_rate）、pending_favored、queued_paths、当前 LLM 调用次数（chat_times）和目标状态 ID（target_state_id）。各状态按"探索效率"（paths_discovered ÷ (selected_times + 1)）升序排序（最卡住的状态排在最前），最多输出 8 个状态，提示 LLM 重点关注这些"瓶颈"状态。

提示词构造使用 json-c 库构建结构化的 JSON 消息，而非手工拼接字符串。提示词的内容远比基线丰富：包含协议名称、当前 IPSM 的节点总数和边总数、上述排序后的状态详细信息、以及明确的指令——要求 LLM 以两种策略之一回复：策略 A 是 suggested_request（建议一个具体的消息序列来探索某个低效率状态），策略 B 是 actions 数组，包含以下结构化操作类型：set_target_state（将目标状态 ID 重定向到指定状态）、prioritize_seeds（将指定种子索引标记为 favored 并更新所有状态的种子选择指针）、propose_mutations（对指定种子的指定字节偏移执行 insert/replace/flip 操作，生成候选并立即通过 common_fuzz_stuff 提交执行）。主路径调用 llm_handle_plateau() 函数（state_ctx 非空时走富提示词路径）；消融实验路径（ablation_no_state_prompt=1）退化为 ChatAFL 原始 construct_prompt_stall_original 提示词，此时 temperature 显式设为 1.2。

在真正发起 LLM 调用之前，会进行提示词哈希去重检查：使用 djb2 算法对 examples + history + state_ctx 的拼接内容计算哈希，与最近 64 个调用的哈希环（LLM_DEDUP_SLOTS = 64）比对。如果命中，跳过本次调用并增加 llm_dedup_hits 计数器，避免相同停滞上下文触发重复的 LLM 请求。

LLM 调用使用 fork 隔离：主进程 fork 一个子进程来执行 HTTP 请求，子进程将结果写入临时文件（out_dir/stall-interactions/llm-suggest-N），并同步写入 .tokens sidecar 文件记录本次调用的 token 消耗（用于 fuzzer_stats 的 llm_prompt_tokens / llm_completion_tokens 累计）。主进程在 waitpid 返回后读取结果文件。如果子进程在 150 秒内没有返回，主进程杀掉子进程并继续运行。这意味着即使 LLM 服务出现超时或故障，模糊测试主循环最多阻塞 150 秒而不会无限挂起。

响应解析使用 llm-validator 模块进行严格的 JSON 模式验证。验证器检查返回的 JSON 是否包含预期的字段名和类型，拒绝不合规的响应。通过验证后，按照操作类型分别处理：set_target_state 操作将全局 target_state_id 重定向到 LLM 指定的状态；prioritize_seeds 操作将指定种子标记为 favored（同时更新所有包含该种子的状态的 selected_seed_index 指针，确保 set_target_state 重定向后仍能生效）；propose_mutations 操作读取指定种子文件，依次对每个操作（insert/replace/flip）生成变异副本并立即通过 common_fuzz_stuff 提交执行和覆盖率采集；suggest_strategy 操作当前为 noop（保留扩展入口）。如果 LLM 返回的是 suggested_request，则直接将该消息序列转换为种子加入队列。

第六阶段：并行协议文法充实

Opt 将文法充实过程从串行改为并行。具体实现是使用 pthread 线程池：当发现多个新消息类型时，为每个消息类型创建一个独立的线程，各线程并行地向 LLM 发起请求。三阶段流水线设计为：第一阶段，主线程收集所有待充实的消息类型；第二阶段，线程池并行执行所有 LLM 请求；第三阶段，主线程汇总所有响应并更新文法知识库。这大幅减少了充实过程对主循环的阻塞时间——如果有 5 个新消息类型需要充实，基线需要 5 倍的串行等待时间，而 Opt 只需要约 1 倍（取决于线程池大小和 LLM 服务的并发能力）。

第七阶段：节点停滞检测

Opt 还实现了一个额外的"节点停滞"机制：在主循环的种子选择阶段，每轮都比较当前 IPSM 全局节点总数（agnnodes(ipsm)）是否有所增长。如果发现增长，重置 node_stagnation_rounds 计数器；否则计数器递增。当 node_stagnation_rounds 超过 80 且全局节点数仍未增长时，以 30% 的概率将本轮的状态选择算法临时切换为 RANDOM_SELECTION（完全随机选态，而非基于得分的 FAVOR 算法），打破"热点锁定"——即避免模糊测试器过度集中于某个看似有潜力但实际已枯竭的状态。30% 的概率设计保证不会完全放弃 FAVOR 算法的主导地位。注意：这里的"停滞"是全局 IPSM 节点总量的停滞（无新协议状态被发现），不是某个具体状态的发现停滞。

三、两者的本质区别与底层逻辑
基线的本质是"被动触发的文本翻译器"。 它的工作模式是：等待一个固定计数器超过固定阈值，然后向 LLM 发送一段不含任何运行时状态信息的文本提示，从 LLM 返回的自由文本中用正则表达式抽取消息序列，加入种子队列。整个过程中，LLM 不知道模糊测试器当前在哪个状态、哪些状态已被充分探索、哪些状态是边界；模糊测试器也不根据 LLM 的响应质量调整后续的提问策略。这是一个没有反馈的单向信息流。

Opt 的本质是"自适应的状态感知协作器"。 它的工作模式是：持续监控边增长率，动态调整 LLM 介入时机；在触发时，将完整的 IPSM 拓扑信息（状态数、边数、每个状态的探索效率、可达种子索引 `seed_ids`）编码为结构化 JSON 传递给 LLM；要求 LLM 返回结构化操作指令而非自由文本；用严格的 JSON 验证器校验响应；将 LLM 的建议转化为三种具体的控制动作（目标状态重定向、种子优先级调整、精确变异点建议）。整个过程形成一个闭环：模糊测试器的运行时状态流入 LLM，LLM 的结构化建议流回模糊测试器并影响其后续行为，而行为的结果又通过下一次的状态上下文反馈给 LLM。

用控制论的框架来理解：

ChatAFL 基线是一个开环控制系统。控制信号（LLM 建议）的生成不依赖于系统的实际输出（覆盖率、状态转移）。阈值是预设的常数，提示词是固定模板，响应解析是脆弱的正则匹配。系统无法自我纠正——如果 LLM 给出了低质量的建议，基线无从知晓，下次停滞时仍然会发送同样模板的提示词。

ChatAFL-Opt 是一个自适应闭环控制系统。它有三个可观测量：边增长率（宏观探索速度）、IPSM 拓扑（微观状态结构）、每状态探索效率（局部饱和度）。它有三个执行器：状态选择权重（控制"去哪里"）、种子优先级（控制"用什么"）、变异建议（控制"改哪里"）。控制律是自适应的：阈值 τ(t) 根据边增长率 Ė 动态调整（Ė>5 → τ=150, 1<Ė≤5 → τ=100, Ė≤1 → τ=50）；前沿加权因子 β 根据出度动态调整（deg⁺≤1 → β=4, deg⁺≤3 → β=2, deg⁺≥4 → β=1），并进一步根据可接受性惩罚修正（error_hint=1 → β×0.25，error_hint=0 且低生产率 → β×0.5，error_hint=2 → 无惩罚）。

这种架构差异导致了实验中观察到的所有性能差异：

边覆盖率全面碾压（10 个目标全胜，平均加 50.5%），根本原因是前沿加权机制将探索资源集中到低出度的边界状态，这些状态正是新转移边最可能被发现的位置。

节点覆盖率中等提升（6 胜 4 平，平均加 7.8%），因为新节点的发现本身就是小概率事件，但状态感知的 LLM 建议能针对性地建议触达未知状态的消息序列，比盲猜更有效。

代码覆盖率稳步提升（分支覆盖 7 胜，行覆盖 8 胜），因为更多的状态转移意味着更多的协议逻辑分支被执行。

初始发现速度显著加快，因为自适应阈值在早期探索放缓时（Ė≤1）迅速将阈值降到 50，比基线的固定 512 快十倍触发 LLM 介入。

吞吐量不受损（部分目标甚至提升），因为并行充实和 fork 隔离的 LLM 调用大幅减少了主循环的阻塞时间，有界循环消除了异常阻塞风险。

==========
Fix-15: 两层假设验证机制 (Two-Tier Hypothesis Validation)
==========
背景问题：
  Fix-9b 为了修复 27% 吞吐量回归，将 validate_and_refine_hypotheses() 从 common_fuzz_stuff()
  热路径中完全移除（__attribute__((unused))）。这导致"假设→验证→反例→精炼"闭环断裂。

解决方案（Fix-15）：
  用两层采样架构代替原来的 per-execution 全量验证：

  Tier-1（采样验证）：在 common_fuzz_stuff() 中每 500 次执行做一次验证
    - 复用已有的 extract_requests() 解析结果（零额外解析开销）
    - 每次最多扫描 8 个 region × N 个假设的约束
    - 性能开销：25000/500 = 50 次/秒 × ~1µs = <0.01%
    - 失败时每 10 次收集一个反例（counterexample）

  Tier-2（周期性精炼）：在 plateau handler 中每 5000 次验证检查一次
    - 如果某假设 fitness < 0.7 且反例 ≥ 3 个，触发 LLM 精炼
    - 每次最多精炼一个假设（限制延迟）
    - 精炼后自动重新集成到 IPSM 模式匹配

  约束检查修复：
    - CONSTRAINT_REGEX：实现 PCRE2 编译匹配（之前为 placeholder return 1）
    - CONSTRAINT_NUMERIC：实现 strtoll 范围检查（之前为 placeholder return 1）
    - CONSTRAINT_ENUM：修复为精确长度+大小写不敏感匹配

闭环数据流：
  common_fuzz_stuff() → [每500次] validate_hypothesis_sampled()
    → 更新 fitness / 收集 counterexample
  plateau_handler → [每5000次验证] periodic_hypothesis_refinement()
    → LLM refine → 更新 schema/constraints → 重新集成到 IPSM
