\begin{abstract}
Stateful protocol fuzzing is difficult because a syntactically valid message can still violate the current session state. This failure mode is amplified when a large language model (LLM) can inject protocol messages into a long-running campaign. We present LoopFuzz, a closed-loop runtime admission-control design for LLM-guided stateful protocol fuzzing. LoopFuzz treats model outputs as bounded hypotheses rather than queue entries. It derives message constraints from RFC fragments, seed traces, and observed responses. It admits an intervention only when runtime evidence supports parseability, response-grounded acceptability, state reachability, and downstream gain. Failed executions become counterexamples for local refinement, and state-aware scheduling triggers model assistance only under adaptive plateau conditions. Re-audited run summaries show that LoopFuzz achieves the highest mean absolute branch coverage on eight of nine off-the-shelf targets and the highest mean IPSM edge count on all nine against AFLNet and ChatAFL. Auxiliary comparisons are mixed: NSFuzz leads absolute branch coverage on five of eight targets, and MQTT remains separately qualified.
\end{abstract}

\section{Introduction}
Network protocol implementations remain difficult security targets because correctness depends on interaction history rather than isolated inputs~\cite{aflnet,stateafl,sgf_usenix22,formatted_stateful_greybox_fuzzing_2024,resolverfuzz_query_response_2024}. An FTP server, for example, rejects a well-formed \texttt{PASS} command if no valid \texttt{USER} command has established the login state. Unlike file fuzzing, protocol fuzzing must preserve message syntax, temporal order, and request-response progress across a multi-step session~\cite{resolverfuzz_query_response_2024,mbfuzzer_mqtt_2025,bleem_packet_sequence_2023,logos_log_guided_fuzzing_2024,diane_identifying_fuzzing_triggers_2021,corecrisis_context_aware_2025}.

Traditional coverage-guided fuzzers work well for stateless parsers. They fit network servers poorly when later behavior depends on earlier valid exchanges~\cite{directed_greybox_fuzzing_2017,seed_selection_successful_fuzzing_2021,one_fuzzing_strategy_rule_2022,regression_greybox_fuzzing_2021,efficient_errors_2022}. Stateful greybox fuzzers such as AFLNet and StateAFL partially close this gap. They infer progress from responses and replay valid traces~\cite{aflnet,stateafl,sgf_usenix22,profuzzbench_benchmark_stateful_protocol_2021,snapfuzz_high_throughput_fuzzing_2022,bleem_packet_sequence_2023,formatted_stateful_greybox_fuzzing_2024}. Even so, byte-level mutation still struggles to synthesize the context-sensitive messages needed to cross deep protocol boundaries.

Large language models offer a plausible source of such messages. ChatAFL and later LLM-assisted fuzzers show that a model can extract structure from specifications, logs, or documentation and produce fluent candidates~\cite{chatafl,fuzz4all_universal_fuzzing_large_2024,llmif_augmented_large_language_2024,matter_llm_specification_2024,carpetfuzz_documentation_2023,prompt_fuzzing_fuzz_driver_2024,large_language_models_are_2023,large_language_models_are_2024}. But fluency is not enough. A request can be grammatically plausible and still be invalid for the live session state. Such executions spend budget without improving queue quality.

LoopFuzz places a runtime admission controller between LLM generation and queue admission. It treats the LLM as a hypothesis generator rather than an oracle. It derives message hypotheses from available RFC fragments, seed traces, and observed responses. It stores failed executions as counterexamples and uses them for counterexample-guided refinement (CEGR) rather than unconstrained regeneration. It also uses inferred protocol state machine (IPSM) feedback to prioritize frontier states and rare transitions, and to trigger assistance only when ordinary mutation stalls. The name \emph{LoopFuzz} emphasizes closed-loop admission and refinement, avoiding any suggestion of formal verification of protocol semantics, model behavior, or server correctness.

The contributions of this paper are as follows:
\begin{itemize}
    \item \textbf{Hypothesis-Driven Message Modeling.} LoopFuzz derives message grammars and field constraints from RFC fragments, seed traces, and observed responses, and maintains them as explicit runtime hypotheses.
    \item \textbf{A Closed-Loop Runtime Admission Boundary.} LoopFuzz inserts a runtime admission controller between the LLM and the queue. The controller checks parseability, response-grounded acceptability, state reachability, and downstream gain before admission.
    \item \textbf{Counterexample-Guided Local Refinement.} LoopFuzz preserves failed request-response traces as counterexamples and uses them to patch one field constraint or production at a time, which constrains model freedom and stabilizes refinement.
    \item \textbf{State-Aware Scheduling.} LoopFuzz leverages IPSM topology, state productivity, and adaptive plateau detection to prioritize underexplored frontier states and to request model assistance only when mutation alone stalls.
    \item \textbf{An Empirical Study of Runtime-Validated Assistance.} We evaluate LoopFuzz on a repeated-run benchmark archive. The study includes nine off-the-shelf primary comparisons against AFLNet and ChatAFL using final \texttt{b\_abs} and \texttt{edges}, auxiliary four-way NSFuzz comparisons on eight targets, a separately qualified MBFuzzer/LoopFuzz Mosquitto comparison, and policy ablations of the evaluated controller.
\end{itemize}

Accordingly, the paper evaluates LoopFuzz as a campaign-control policy, not as a standalone message generator. In stateful protocol fuzzing, generation matters only when it survives runtime evidence and improves downstream queue quality.

\subsection{Coverage-Guided Fuzzing vs. Network Targets}
A coverage-guided fuzzer operates through a repeated feedback cycle of seed selection, mutation, execution, coverage measurement, and novelty-based queue update~\cite{seed_selection_successful_fuzzing_2021,one_fuzzing_strategy_rule_2022,regression_greybox_fuzzing_2021,efficient_errors_2022}.
This loop is effective for file parsers, but network targets impose three constraints that matter here:
\begin{enumerate}
    \item \textbf{Temporal state dependence:} server behavior depends on the order and semantics of earlier messages, not only on the current payload~\cite{aflnet,stateafl,sgf_usenix22,formatted_stateful_greybox_fuzzing_2024}.
    \item \textbf{Strict message format:} protocols require delimiters, field layouts, and often checksum or length consistency, so many mutated messages die before they reach deeper logic~\cite{gramatron_effective_grammar_aware_2021,griffin_grammar_free_dbms_2022,formatted_stateful_greybox_fuzzing_2024}.
    \item \textbf{Execution instability:} sockets, forking daemons, and asynchronous response handling complicate both coverage collection and campaign throughput~\cite{snapfuzz_high_throughput_fuzzing_2022}.
\end{enumerate}

\subsection{Stateful Greybox Fuzzing (SGF)}
SGF addresses this gap by treating the target as an \emph{inferred protocol state machine} (IPSM). Formally, the IPSM can be viewed as a Mealy machine $M = (Q, I, O, \delta, \lambda, q_0)$, where:
\begin{itemize}
    \item $Q$ is the set of inferred protocol states;
    \item $I$ is the set of client messages;
    \item $O$ is the set of observed server responses;
    \item $\delta$ maps a state and input to a successor state;
    \item $\lambda$ maps a state and input to an observed response; and
    \item $q_0$ is the initial connection state.
\end{itemize}

AFLNet-style fuzzers infer $Q$ from observed responses and use that structure to bias later exploration toward rare or promising parts of the protocol. Here, the IPSM matters for one reason. It gives LoopFuzz a notion of progress that is richer than raw edge coverage alone.

\subsection{LLM Integration into Protocol Fuzzing}
Large language models make it easier to propose structure-aware protocol messages from RFC text, interaction history, or observed responses. That helps with syntax and message diversity, but it does not solve the harder control problem: a fluent request can still be wrong for the live session state.

Consider an FTP fuzzing campaign against ProFTPD, as illustrated in Fig.~\ref{fig:motivation}. The fuzzer executes \texttt{USER} and \texttt{PASS}. It then queries the LLM for the next request. The model returns \texttt{RETR example\_file.txt}. The request is syntactically fluent but semantically premature. The client lacks an active data channel via \texttt{PASV} or \texttt{PORT}. The server rejects it with \texttt{425 Use PORT or PASV first}.

We call this failure \emph{semantic drift}. The request is locally plausible, but it violates the precondition of the current session state. An open-loop LLM fuzzer admits the request because it looks fluent. It then mutates a rejected branch instead of crossing the missing state transition. LoopFuzz blocks this drift at the admission boundary. The controller treats the \texttt{425} reply as negative evidence. It rejects the candidate and records the failed trace as a counterexample. CEGR then repairs the missing \texttt{PASV}/\texttt{PORT} precondition instead of regenerating the full continuation. This example captures the paper's central claim: the value of LLM assistance depends on runtime admission, not on surface fluency. We use semantic drift as an operational motivation for rejection and CEGR repair, not as a separately estimated global rate.

\section{Related Work}
We position LoopFuzz against the prior lines that are closest in mechanism and evaluation.

Earlier structure-aware fuzzing used explicit message structure, inferred snippets, token constraints, or grammar-level guidance to preserve validity~\cite{snipuzz_black_box_fuzzing_2021,token_level_fuzzing_2021,gramatron_effective_grammar_aware_2021,griffin_grammar_free_dbms_2022,no_grammar_no_problem_2023,likely_invariants_feedback_2021,mundofuzz_grammar_inference_2022}. These systems improve input quality. They do not address the control problem that arises when an external model proposes state-dependent protocol messages.

Stateful greybox and state-aware network-service fuzzing address protocol interaction more directly. AFLNet, StateAFL, NSFuzz, and the broader SGF line infer or expose state structure from server responses, process memory, or program variables~\cite{aflnet,stateafl,nsfuzz,sgf_usenix22,profuzzbench_benchmark_stateful_protocol_2021}. They then use that structure to prioritize rare or productive traces.

Later systems extend this idea to packet-sequence exploration, format-sensitive protocol fuzzing, and communication-heavy environments~\cite{bleem_packet_sequence_2023,formatted_stateful_greybox_fuzzing_2024,logos_log_guided_fuzzing_2024,msgfuzzer_message_sequence_guided_2024,resolverfuzz_query_response_2024,mbfuzzer_mqtt_2025,fuzzusb_hybrid_stateful_fuzzing_2022,dtls_fuzzer_dtls_protocol_2022,edhoc_fuzzer_edhoc_protocol_2023,tron_fuzzing_linux_network_2025}. LoopFuzz builds on this line, but adds a runtime-validated admission boundary for LLM interventions. SGF, NSFuzz, Bleem, Logos, and MBFuzzer are therefore important external comparison points beyond AFLNet and ChatAFL. The present evaluation archive does not include direct head-to-head reproduction against that broader set, so we treat that omission as a limitation rather than as evidence that those systems are weaker.

Adjacent work studies state-aware or interaction-heavy fuzzing in robotic policies, firmware, Linux drivers, data-distribution middleware, hardware, and embedded systems~\cite{pgfuzz_policy_guided_fuzzing_2021,android_smarttvs_vulnerability_discovery_2021,fuzzware_mmio_2022,statefuzz_linux_driver_2022,differential_fuzzing_data_distribution_2024,fuzzing_hardware_like_software_2022,coverage_guided_fuzzing_embedded_2023}. These systems are not protocol fuzzers in the narrow sense. They still support the broader point that state feedback and interaction context can dominate raw mutation quality.

Target-aware scheduling and semantic validation form another relevant line. Directed greybox fuzzing studies how to steer search toward high-value targets~\cite{directed_greybox_fuzzing_2017,windranger_blocks_2022,when_analysis_2025}. Work on seed selection and strategy adaptation studies how to spend budget more effectively~\cite{seed_selection_successful_fuzzing_2021,one_fuzzing_strategy_rule_2022,regression_greybox_fuzzing_2021,efficient_errors_2022}. Semantic validation and fuzz-driver generation show that stronger inputs often require an explicit acceptance interface~\cite{one_engine_to_fuzz_em_all_2021,apicraft_fuzz_driver_2021}. LoopFuzz inherits that lesson and applies it to LLM proposals.

Related work also studies how to infer dependencies or exploit guidance from data-flow and learned signals outside protocol fuzzing proper~\cite{rulf_rust_library_fuzzing_2021,smartian_analyses_2021,magneto_step_wise_approach_2024}. This line reinforces our decision to treat the LLM as a bounded proposal mechanism rather than as an unconstrained generator.

LLM guidance addresses the synthesis bottleneck more directly. ChatAFL uses RFCs and interaction histories to generate protocol messages~\cite{chatafl}. Adjacent systems use LLMs for general fuzz input generation and documentation-guided constraint extraction~\cite{fuzz4all_universal_fuzzing_large_2024,llmif_augmented_large_language_2024,docter_documentation_guided_fuzzing_2022,carpetfuzz_documentation_2023}. Other systems use LLMs for specification-guided device fuzzing or fuzz-driver generation~\cite{matter_llm_specification_2024,prompt_fuzzing_fuzz_driver_2024}. Our work is closest to ChatAFL. The difference is the control boundary. LoopFuzz asks whether a proposal should be admitted, whether its hypothesis survives runtime evidence, and how the IPSM should guide the next query.

Benchmarking practice is also part of the context. ProFuzzBench established a reusable baseline for repeated protocol-fuzzing experiments~\cite{profuzzbench_benchmark_stateful_protocol_2021}. Recent methodology work shows how easily comparisons become unstable without fixed budgets, repeated trials, and careful interpretation of coverage signals~\cite{sok_prudent_evaluation_practices_2024,reliability_benchmarking_2022,many_stack_2022}. We follow that guidance because runtime-validated assistance is especially sensitive to campaign history.

LoopFuzz preserves the stateful greybox fuzzing execution path. It sets a strict control boundary between LLM generation and queue admission. A model output changes the campaign only after runtime evidence supports admission. The admission rule checks message structure, parseability, response behavior, inferred state reachability, and downstream campaign value. The method has four coupled components: grammar hypothesis generation, runtime admission control, counterexample-guided refinement, and state-aware scheduling.

This control boundary is the core idea of the paper. ChatAFL is open-loop: it uses a fixed trigger, a plain-text prompt, and direct admission of the extracted request. LoopFuzz is closed-loop: IPSM growth, state productivity, and hypothesis fitness determine when the LLM is queried, what context it receives, and whether its output is admitted.

The three loops in Fig.~\ref{fig:arch} define the analytical roles of the method. The Grammar Hypothesis Loop constructs and repairs message hypotheses from RFC knowledge, seed traces, and observed responses. The Fuzz Execution Loop performs state selection, mutation, bounded execution, IPSM update, and novelty checking. The LLM Intervention Loop is activated only under plateau conditions and returns either a validated continuation or a bounded control action.

The remaining labels in Fig.~\ref{fig:arch} denote control interfaces rather than independent claims. \emph{Tier-1 Sampling} is the cheap online check over parsed execution regions. \emph{Tier-2 Refinement} is the counterexample-triggered repair path. \emph{Schema validation} checks the structure of a model reply before bounded action dispatch. \emph{Bounded action dispatch} maps an admitted action to one of three campaign controls: mutation proposal, seed prioritization, or target-state redirection. The \emph{prompt reuse filter} prevents repeated prompts over the same state summary. Query isolation bounds failures in the model-query path.

\subsection{Grammar Hypothesis Loop}
Let $\mathcal{L}(c, s, \Sigma)$ denote the LLM generation function under prompt context $c$, state summary $s$, and protocol knowledge $\Sigma$. LoopFuzz uses $\mathcal{L}$ in two stages. During initialization, it preserves ChatAFL's template extraction and seed enrichment path. Initial enrichment is scheduled as a bounded phase so that corpus diversification does not dominate early campaign time. During fuzzing, LoopFuzz adds a lazily initialized hypothesis layer. This layer is activated at the first plateau event and updated through sampled validation and refinement. The separation is important. The initialization phase broadens the initial seed set. Runtime hypotheses support runtime-validated control during long campaigns.

The Grammar Hypothesis Loop draws on three evidence sources when they are available: RFC fragments, queued seed traces or packet examples, and observed server responses, including response codes and error texts. For each message type $m$, the loop maintains a hypothesis $h_m=(G_m,\Phi_m)$. Here, $G_m$ is an ABNF-style or template-style production, and $\Phi_m$ is a set of field constraints. In LoopFuzz, $\Phi_m$ captures length bounds, enumerated values, token dependencies, and simple cross-field relations. This representation is more constrained than free-form text and lighter than a full formal protocol specification. We choose it because sampled online validation must remain cheap.

The evidence sources are not assumed to be complete. RFC extraction supplies useful protocol structure when a relevant fragment is available. Seed traces provide executable examples of message order and framing. Observed responses provide target-specific evidence about rejection, progress, and state change. This division is important for the claim. LoopFuzz does not require a full protocol specification. It requires enough evidence to form testable hypotheses and then lets runtime admission decide whether those hypotheses should affect the campaign.

\subsection{Runtime Admission Controller}
The runtime admission controller is the central mechanism in our design. It does not formally prove correctness. Instead, it enforces four runtime checks before an LLM contribution can affect the campaign: parseability, acceptability, state reachability, and coverage gain. A candidate intervention $x$ is admitted only if
\[
A(x)=P(x) \land U(x) \land R(x) \land G(x),
\]
where $P$ denotes local parseability, $U$ denotes response-grounded acceptability, $R$ denotes evidence of new or redirected state reachability, and $G$ denotes downstream gain in IPSM structure or coverage.

The FTP example in Fig.~\ref{fig:motivation} illustrates the same checks. The candidate \texttt{RETR example\_file.txt} can satisfy local syntax under $P$, but the live \texttt{425} response makes $U$ fail because no data channel has been negotiated. The failed execution also provides no useful new transition or coverage signal, so $R$ and $G$ do not support admission. LoopFuzz therefore rejects the candidate and records a counterexample that constrains CEGR to repair the missing \texttt{PASV}/\texttt{PORT} precondition.

\subsubsection{Structured Output and Parseability}
The plateau stage accepts either a concrete next-request candidate or a bounded structured-action object. Runtime validation first checks structural well-formedness, field types, length bounds, and action-schema consistency. LoopFuzz then tests local parseability against the current message hypotheses. It reuses parsed message regions already available during ordinary execution. This step rejects structurally invalid interventions before they perturb campaign control.

\subsubsection{Response-Grounded Acceptability}
Parseability alone is insufficient. A parsed request can still be semantically premature. LoopFuzz therefore classifies the resulting response and treats a non-rejection response as positive evidence. Rejected or persistently unproductive responses reduce state productivity and hypothesis fitness. This gives an execution-grounded notion of acceptability rather than a semantic proof. The controller asks a narrow question: does live target behavior support admission?

\subsubsection{State Reachability and Coverage Gain}
The final admission question is whether a candidate helps the campaign. LoopFuzz measures this with the standard AFLNet-style novelty test on new IPSM states, new IPSM transitions, or new edge coverage. The controller therefore uses an IPSM-derived reachability signal, not text quality alone. A hypothesis fragment remains in active use only when execution provides positive evidence in state reachability or coverage. Fluent but repeatedly unproductive candidates are filtered out at the control boundary instead of accumulating as low-value queue bias.

\subsection{Counterexample-Guided Refinement}
When sampled validation fails repeatedly, LoopFuzz records a concrete counterexample. The record contains the failure-triggering request fragment, the observed response, and the mismatch against the current hypothesis. Refinement is deliberately local. Instead of rewriting the full protocol description, the refinement interface constrains each repair to one field constraint or one production fragment. This single-patch discipline narrows the model's search space, limits unconstrained edits, and makes the repair path auditable. The resulting update is reintegrated into protocol matching and re-evaluated by later sampled validation.

This repair boundary is intentionally weaker than formal grammar repair. The one-field or one-production constraint is enforced through the refinement prompt and audit log, not through hard AST differencing. The current implementation also stores concrete failed traces without counterexample minimization. We therefore claim bounded local refinement, not complete protocol inference.

\subsection{State-Aware Scheduling and Plateau-Triggered Assistance}
Reducing malformed generations solves only half of the problem. Stateful fuzzers also stagnate when the campaign keeps revisiting locally dense IPSM regions while failing to cross narrow protocol bridges. LoopFuzz therefore treats IPSM feedback as a first-class scheduling signal.

To address this, LoopFuzz augments state selection with a frontier bonus $\beta$ derived from the out-degree of the IPSM:
\[
\beta = \begin{cases}
4.0 & \text{if } \deg^+(s) \le 1 \\
2.0 & \text{if } \deg^+(s) \le 3 \\
1.0 & \text{otherwise}
\end{cases}
\]
States absent from the IPSM receive the maximum bonus $\beta{=}4$. LoopFuzz then modulates this bonus with a three-level error-productivity hint: unknown, likely error, or confirmed productive. The reported implementation encodes these levels as 0, 1, and 2. This hint downweights frontier states that repeatedly behave like rejection sinks, but it does not discard them outright.

In the reported policy, hint level 1 applies a $\beta{\times}0.5$ penalty. Hint level 0 is reduced to $\beta{\times}0.7$ only after repeated low-productivity selections ($\mathit{selected\_times}{\ge}30$ and $\mathit{productivity}{<}0.005$). Hint level 2 receives no penalty. The hint is initialized from response-code classification and updated online. As a result, states can be promoted or demoted as evidence accumulates. They are not fixed by an early response pattern. This policy approximates a rare-transition preference without requiring an exact model of the full protocol state space.

These constants should be read as the reported control policy, not as a claim of global optimality. The three frontier-bonus levels $\{4.0,2.0,1.0\}$ separate unseen or low-out-degree frontier states from denser regions by coarse preference rather than by fine-grained tuning. The error-productivity penalties and the $(30,0.005)$ gate reduce repeated investment in response-derived rejection sinks. They still allow those states to recover if later executions become productive. Likewise, the $(80,30\%)$ node-stagnation safeguard and the 64-call intervention budget are bounded control parameters. They prevent persistent hot-spot lock-in and unbounded LLM overhead. We report them to make the policy auditable. This study does not claim a full sensitivity analysis over the entire hyperparameter surface.

A complementary graph stagnation check tracks whether IPSM growth has collapsed at the graph level rather than only at the local state level. When no new nodes appear for an extended interval, the scheduler intermittently injects random selection to avoid persistent hot-spot lock-in. In the reported configuration, that safeguard activates after 80 consecutive rounds without node growth and uses a 30\% random-selection probability.

Plateau detection uses the IPSM edge growth rate $\dot{E}$, measured as edges gained per minute. LoopFuzz recalculates this rate every 60 seconds of wall-clock time and uses it to set an adaptive threshold:
\[
\tau(\dot{E}) = \begin{cases}
300 & \text{if } \dot{E} > 5 \\
200 & \text{if } 1 < \dot{E} \le 5 \\
150 & \text{if } \dot{E} \le 1
\end{cases}
\]
The initial value is $\tau{=}200$ for textual protocols. MQTT uses the higher thresholds $\{500,400,300\}$ under the same edge-growth bins because binary framing and broker-mediated behavior expose state progress more sparsely. More generally, LoopFuzz treats plateau triggering as a rate-sensitive control decision, not as a fixed-frequency query rule.

Assistance is invoked only when edge growth remains weak and the model-intervention budget is not exhausted. In the reported configuration, the plateau path opens when the unproductive streak reaches $\tau$ and prior model interventions remain below 64. Once inside that path, hypotheses are initialized lazily on first use. Refinement remains gated by validation count and accumulated counterexamples. The prompt reuse filter covers the most recent 64 LLM invocations. This prevents assistance from reacting to the same state summary again and again.

The plateau prompt exposes a compact state summary rather than a raw execution log. It includes IPSM node and edge counts, the current edge-growth rate, pending favored seeds, queued paths, the current target state, and the least productive states. The admissible action space is also bounded. A model can redirect the target state, reprioritize a small set of seeds, or propose bounded mutations over an existing seed. These actions are not admitted because they are fluent. They must still pass the same runtime admission boundary. This design keeps the LLM in the role of a state-directed policy proposer.

MQTT-specific scheduling is treated as a protocol adaptor, not as the general mechanism of LoopFuzz. For MQTT campaigns, packet-type selection uses a state-indexed action policy, and mutation-family selection uses a bandit-style controller. These signals help expose broker forwarding behavior to the IPSM, but the paper reports Mosquitto separately because this adaptor is protocol-specific and because MBFuzzer is a specialized MQTT baseline. In short, assistance is conditional, budgeted, state-directed, and scoped by protocol evidence.

LoopFuzz also supports protocol-adaptor signals that are not used as headline evidence in the primary table. For MQTT, the adaptor translates between binary packets and textual hypotheses, drives multi-party broker interactions, and records differential behavior across broker-facing roles. A lightweight protocol oracle can log semantic violations such as authentication bypass, state-order violations, information leaks, traversal patterns, injection patterns, or denial-of-service indicators. These signals are useful for auditing and for later bug triage. They are not treated as confirmed vulnerabilities in this paper because crash deduplication, root-cause analysis, exploitability review, and cross-target oracle calibration are not normalized across the archive.

Algorithm~\ref{alg:fuzz} specifies the plateau path and the hypothesis-refinement gate. It formalizes how state-aware triggering, runtime admission checks, and CEGR interact within one campaign loop.

\begin{algorithm}[!tbp]
\caption{Runtime-Validated Plateau Recovery in LoopFuzz}
\label{alg:fuzz}
\SetAlgoLined
\SetAlgoNlRelativeSize{0}
\footnotesize
\DontPrintSemicolon
\KwIn{Target $T$, LLM interface $\mathcal{L}$, corpus $C$, edge-growth signal $\dot{E}$}
\KwOut{Coverage bitmap $\mathcal{B}_{global}$ and IPSM $\mathcal{M}$}
Initialize $\mathcal{B}_{global}$ and $\mathcal{M}$\;
\While{the campaign budget remains}{
    $s \leftarrow \textsc{SelectSeed}(C,\mathcal{M})$\;
    $(trace,Q) \leftarrow \textsc{MutateExecute}(T,s)$\;
    Update $\mathcal{B}_{global}$, $\mathcal{M}$, and frontier scores from $(trace,Q)$\;
    \If{sampled validation is due}{
        Validate active hypotheses on parsed regions of $Q$\;
    }
    \If{the adaptive plateau gate opens}{
        Initialize hypotheses on first use, if needed\;
        \If{counterexample evidence opens the refinement gate}{
            Patch the lowest-fitness hypothesis locally\;
        }
        $c \leftarrow \textsc{BuildPrompt}(\mathcal{M},C,Q,\dot{E})$\;
        \If{$c$ is not in the recent prompt cache}{
            $r \leftarrow \mathcal{L}(c)$ under process isolation\;
            Admit $r$ only if parseability, acceptability, reachability, and gain all hold\;
            Apply the admitted bounded action to $C$\;
        }
    }
}
\end{algorithm}

This integration also imposes a bounded operating model. The initial enrichment phase is separated from long-running admission control so that seed completion does not dominate early wall-clock time. Hypothesis construction is deferred until the first plateau event. This avoids paying the full refinement cost before the campaign exposes evidence of stagnation. Model queries use process isolation, and network cleanup is bounded to limit persistent stalls on forking daemons. These mechanisms are not separate novelty claims. They define the operating conditions under which runtime admission remains compatible with long-running stateful fuzzing.

\section{Experimental Evaluation Design}

We organize the evaluation around three research questions that match the paper's main claims. We ask whether closed-loop admission control changes whole-campaign behavior, whether the evaluated state-aware control policy helps campaigns escape IPSM plateaus, and whether those effects persist in final 24-hour outcomes.
\begin{itemize}
    \item \textbf{RQ1 (Whole-Campaign Effect):} Does runtime-validated LLM assistance prevent the coverage regressions that can arise from direct open-loop generation?
    \item \textbf{RQ2 (IPSM Escape Dynamics):} Does the evaluated state-aware policy, with frontier scheduling and plateau-triggered intervention, sustain IPSM growth after the baselines stall?
    \item \textbf{RQ3 (End-of-Campaign Outcome):} Under equal 24-hour budgets, how does LoopFuzz affect final \texttt{b\_abs} and final \texttt{edges} relative to prior stateful greybox baselines?
\end{itemize}

\subsection{Experimental Setup}
We ran all experiments on a dedicated Ubuntu 20.04 server with 32 CPU cores and 64GB RAM. The benchmark suite spanned 10 implementations across seven protocol families:
\begin{enumerate}
    \item \textbf{FTP:} LightFTP, bftpd, ProFTPD, and Pure-FTPd.
    \item \textbf{SMTP:} Exim.
    \item \textbf{RTSP:} Live555.
    \item \textbf{SIP:} Kamailio.
    \item \textbf{DAAP/DACP:} Forked-daapd.
    \item \textbf{HTTP:} Lighttpd1.
    \item \textbf{MQTT:} Mosquitto.
\end{enumerate}

The benchmark suite contains 10 targets, but the provided run-summary archive supports different comparisons on different subsets. The primary comparison uses AFLNet, ChatAFL, and LoopFuzz on the nine off-the-shelf non-MQTT targets: LightFTP, bftpd, ProFTPD, Pure-FTPd, Exim, Live555, Kamailio, Forked-daapd, and Lighttpd1. We retain only completed runs with at least 1400 archived minutes. If a fuzzer-target pair contains more than 10 valid runs, we keep the lowest 10 run IDs. This rule leaves six eligible LightFTP ChatAFL runs and trims extra LoopFuzz rows for targets with more than 10 valid runs. The audit is based on the updated primary, ablation, NSFuzz, and MBFuzzer result archives.

Mosquitto needs separate treatment. In the provided archive, the Mosquitto rows do not form the same 24-hour three-way comparison as the nine primary targets. AFLNet has 10 completed 24-hour rows. The available LoopFuzz Mosquitto rows report \texttt{b\_abs} and \texttt{edges}, but their runtimes range from 31 to 444 minutes, with a mean of 137.4 minutes. MBFuzzer provides a Mosquitto summary under its own \texttt{branch\_covered} counter rather than the AFLNet-lineage run-summary format. We therefore report Mosquitto as a separately qualified MQTT auxiliary comparison rather than pooling it with the primary 24-hour table.

The equal-budget primary subjects are textual request/response protocols. Mosquitto is treated separately through an MQTT-specific adaptor. We restrict our claims to this regime. The method has not been validated on opaque binary or encrypted protocols such as DNS, TLS, SSH, DTLS, or DICOM.

Both ChatAFL and LoopFuzz used the same pinned \texttt{GPT-4o-mini} endpoint. Prompts remained protocol-agnostic beyond protocol name, observed state, and runtime summary. We did not hand-specialize prompt text per target. The primary table uses approximately 24-hour archived repeated runs under the deterministic selection rule above, with no per-system cherry-picking of directories or best runs. MQTT is excluded from that equal-budget primary table because the available rows do not provide a comparable three-way 24-hour archive.

\subsection{Baselines, Metrics, and Statistical Protocol}
We used two baseline layers. The \emph{primary} baselines were AFLNet as the stateful greybox baseline and ChatAFL as the direct LLM-assisted baseline. The \emph{auxiliary} reproduced baselines were NSFuzz~\cite{nsfuzz} on eight non-HTTP/non-MQTT targets and MBFuzzer~\cite{mbfuzzer_mqtt_2025} on Mosquitto. For NSFuzz, we compare AFLNet, ChatAFL, LoopFuzz, and NSFuzz side by side using the archived \texttt{b\_abs} and \texttt{edges} fields. For MBFuzzer, we compare only a coverage-like endpoint because MBFuzzer's summary does not expose the AFLNet-lineage \texttt{b\_abs} or \texttt{edges} fields.

The main dependent variables are final \texttt{b\_abs} and final \texttt{edges}. The \texttt{b\_abs} field is the absolute branch-coverage count in the run-summary archive. The \texttt{edges} field is the archived IPSM edge count and is used as a state-exploration diagnostic. For NSFuzz, \texttt{edges} is an artifact-level field. We do not treat it as semantically identical to the response-derived IPSM transition abstraction maintained by the primary AFLNet-lineage fuzzers.

For each primary target and metric, we summarized selected terminal values with mean and sample SD. We then applied a two-sided exact Mann-Whitney U test to the per-run terminal values. The tables report terminal aggregates only, not significance at every timestamp. We also preserved crash artifacts, but this study does not claim novel vulnerabilities because crash triage and root-cause validation are not normalized across the suite.

\subsection{Policy-Ablation Design}
The ablation design follows the switches present in the provided ablation archive. The archived matrix compares the evaluated full controller against four policy perturbations: disabling CEGR, disabling frontier scheduling, disabling hypothesis validation, and disabling adaptive triggering. This organization reflects the actual archive rather than an idealized orthogonal factorization. We apply the same deterministic run-selection rule as the primary comparison: keep completed runs with at least 1400 minutes, and if more than 10 valid runs remain, keep the lowest 10 run IDs.

\subsection{Trace Accounting and Cost Reporting}
Because LoopFuzz is a closed-loop LLM-in-the-loop system, coverage alone is not enough for accounting. We therefore logged each plateau event with its prompt, raw model reply, and token use. We also logged each refinement event with the affected hypothesis and its counterexamples. The ProFTPD semantic-drift example in Fig.~\ref{fig:motivation} is a concrete instance of this evidence pattern: candidate request, target response, admission decision, and refinement target. These logs are sufficient to recover target-level admission statistics such as parseability pass rate, response-grounded acceptance rate, and CEGR repair outcomes. Those summaries are not normalized across the full archive. We therefore report them as audit artifacts and as a limitation rather than as aggregate evidence. As a result, semantic drift remains a motivating failure mode and an auditable trace category here, not a quantified cross-target headline metric.

The four data directories audited here do not contain a normalized cross-target LLM-cost summary. We therefore do not make a cost-efficiency claim in this re-audited experimental section.

\subsection{RQ1: Whole-Campaign Effect}
LoopFuzz is evaluated here as an integrated control policy, not as an isolated rejection heuristic. Table~\ref{tab:24h_results} shows that direct open-loop assistance is not uniformly robust under the selected archived runs. ChatAFL ties AFLNet on LightFTP, finishes below AFLNet on Exim in \texttt{b\_abs}, is close to AFLNet on Forked-daapd, and improves several other targets. Under these conditions, improved generation alone does not consistently translate into stronger end-of-campaign coverage.

Across the nine primary targets, LoopFuzz reaches the highest mean final \texttt{b\_abs} on eight targets: LightFTP, bftpd, ProFTPD, Pure-FTPd, Exim, Live555, Kamailio, and Lighttpd1. AFLNet remains highest on Forked-daapd. Exact Mann-Whitney testing narrows the strongest \texttt{b\_abs} evidence to Pure-FTPd, Exim, Live555, and Lighttpd1. The robust coverage claim supported by the audited summaries is therefore bounded: LoopFuzz improves the closest AFLNet/ChatAFL lineage on most, but not all, primary targets.

Table~\ref{tab:aux_results} shows that the broader NSFuzz baseline picture is mixed. Across the eight NSFuzz targets, NSFuzz has the highest \texttt{b\_abs} on LightFTP, Pure-FTPd, Exim, Kamailio, and Forked-daapd. LoopFuzz has the highest \texttt{b\_abs} on bftpd, ProFTPD, and Live555. For reported \texttt{edges}, LoopFuzz is highest on seven targets, while NSFuzz is highest on Forked-daapd. Table~\ref{tab:mqtt_aux} separately reports MQTT. The available LoopFuzz Mosquitto rows have higher archived \texttt{b\_abs} and \texttt{edges} than the available AFLNet rows, but they are much shorter. MBFuzzer reports \texttt{branch\_covered} under its own 24-hour summary, which is not directly comparable to the AFLNet-lineage \texttt{b\_abs} field.

\subsection{RQ2: IPSM Escape Dynamics}

On terminal \texttt{edges}, LoopFuzz attains the highest mean on all nine primary targets. The strongest same-target evidence appears on LightFTP, bftpd, ProFTPD, Pure-FTPd, Exim, and Live555, where the LoopFuzz \texttt{edges} win is significant versus both AFLNet and ChatAFL under the two-sided exact Mann-Whitney test. Kamailio, Forked-daapd, and Lighttpd1 remain positive but descriptive against at least one primary baseline. The NSFuzz auxiliary rows point in the opposite direction on Forked-daapd, where NSFuzz reports higher \texttt{edges}; on the other seven NSFuzz targets, LoopFuzz has higher reported \texttt{edges}.

\subsection{RQ3: End-of-Campaign Outcome}

The \texttt{b\_abs} comparison is less uniform than the \texttt{edges} comparison once NSFuzz is included. In the primary three-way comparison, LoopFuzz is strongest by mean on eight of nine targets and does not lead Forked-daapd. In the auxiliary NSFuzz comparison, NSFuzz is strongest in \texttt{b\_abs} on five of eight targets. This distinction matters for interpretation: the audited archive supports a strong primary-lineage state-exploration result and a broad but still selective absolute-branch-coverage result, not a blanket dominance claim over all specialized fuzzers.

\subsection{Ablation: Policy Perturbations}

Table~\ref{tab:ablation_results} reports the archived policy ablations as deltas relative to the evaluated full controller. Each cell shows $\Delta$ \texttt{b\_abs} / $\Delta$ \texttt{edges}. The updated archive shows a mixed rather than monotone pattern. Removing CEGR improves mean \texttt{b\_abs} only on ProFTPD (+100.8) and Live555 (+1.2), while reducing it on the other seven primary targets. Removing frontier control reduces mean \texttt{b\_abs} on all nine targets, but its effect on \texttt{edges} is not uniformly negative. Removing adaptive triggering improves some endpoints on Pure-FTPd, Live555, Kamailio, and Lighttpd1, while degrading others. The audited ablations therefore do not support a claim that every exposed sub-control is individually necessary across all targets.

The strongest lesson from the ablation archive is that controller switches interact with target behavior. Disabling hypothesis validation or disabling adaptive triggering can improve \texttt{b\_abs} on some targets but degrade \texttt{edges} on others. This reinforces an integrated-policy interpretation rather than a clean per-module causal decomposition.

\section{Discussion}

The paper makes one central claim. In stateful protocol fuzzing, LLM generation is useful only when it is governed by a strict admission boundary. ChatAFL already showed that an LLM can generate protocol text~\cite{chatafl}. LoopFuzz asks a different question: when should such output be trusted by the campaign? Our answer is closed-loop runtime admission control. It checks structure, parseability, response-grounded acceptability, state reachability, and downstream gain before an LLM suggestion can strengthen the queue. This changes the role of the LLM from queue producer to hypothesis proposer.

The admission controller and the scheduler solve different parts of the same problem. Admission control filters low-value suggestions. It does not decide where to spend the recovered budget. State-aware scheduling decides where to search. Without closed-loop intervention, however, it still depends on ordinary mutation to cross semantic bottlenecks. LoopFuzz combines the two because admission control and state-directed search reinforce each other.

The results also show why response-derived state counts must be read carefully. A campaign can accumulate superficially different rejection paths without moving toward high-value logic. LoopFuzz therefore reads state exploration together with \texttt{b\_abs} and demotes states that remain unproductive over repeated selections. In this setting, productive states matter more than raw state counts. For that reason, \texttt{edges} is best interpreted as a companion diagnostic for campaign behavior, not as a substitute for absolute branch coverage.

The present method is evaluated on textual or semi-textual protocols whose message regions can be parsed cheaply and whose responses provide useful progress signals. That scope covers the benchmark suite used here and many request-response protocols of practical interest. Opaque binary or encrypted protocols require stronger parsers, auxiliary instrumentation, or richer response abstractions. Response codes alone may not expose state reachability in those settings. That extension matters, but it lies beyond the current empirical scope.

The present evaluation is also centered on campaign-control behavior rather than on vulnerability yield. We preserve crashes and queue artifacts, but we do not report new CVEs or newly confirmed bugs in this study because crash deduplication, exploitability review, and cross-target triage remain incomplete under one uniform protocol. The paper should therefore be read as evidence about campaign control and exploration quality, not as an end-to-end demonstration of stronger bug-finding yield.

Counterexample-guided local refinement is also a deliberate design choice. Repeated unconstrained regeneration does not accumulate persistent knowledge. Local refinement turns failed executions into stored evidence. It makes runtime evidence cumulative rather than disposable. At the same time, the ablation table shows that the exposed refinement switch is not uniformly decisive on every target. The novelty therefore lies in the control interface between model output and system execution, not in prompt wording alone.

\section{Threats to Validity}

\textbf{Internal validity:} LLM-assisted fuzzing remains sensitive to generation variance, target nondeterminism, and campaign-level timing effects. We mitigate these threats by fixing the execution environment, pinning the model endpoint, using low temperatures for grammar extraction and refinement, and designing the campaign matrix around repeated 24-hour runs. Even so, plateau triggering and hypothesis refinement are history-dependent. Early differences can propagate into late-campaign variance. The study also cannot cleanly separate model variance from control-policy variance because both act within the same long-running campaigns.

\textbf{External validity:} The benchmark suite spans 10 implementations across seven protocol families, but the audited primary three-way comparison covers the nine off-the-shelf non-MQTT targets that contain comparable AFLNet, ChatAFL, and LoopFuzz rows. The evidence is therefore strongest for textual or semi-textual protocols whose progress is visible in responses. We do not claim unchanged transfer to opaque binary or encrypted protocols without stronger format-specific adaptors. We include auxiliary NSFuzz comparisons on eight targets and an MQTT comparison involving AFLNet, LoopFuzz, and MBFuzzer, but those rows are target- and artifact-specific rather than a unified cross-system state-machine comparison.

\textbf{Construct validity:} We use final \texttt{b\_abs} and final \texttt{edges} as the main proxies for fuzzing effectiveness in the audited summaries. These are archive-level measurements, but neither fully captures semantic protocol progress. The MBFuzzer \texttt{branch\_covered} field is reported separately because it is not the same artifact field as AFLNet-lineage \texttt{b\_abs}. Our closed-loop runtime admission boundary refers to structured output checks, sampled hypothesis checks, response-grounded acceptability, state-reachability signals, and counterexample-guided refinement. It does not mean formal verification or a perfect pre-execution oracle. We also do not currently report cross-target admission summaries such as parseability pass rate, response-grounded acceptance rate, or CEGR repair success rate. The motivating semantic-drift narrative is therefore operationalized through logs rather than reduced to one global prevalence number.

\textbf{Reproducibility validity:} We reduce fairness ambiguity where possible. ChatAFL and LoopFuzz share the same pinned model endpoint. Each primary target is drawn from one declared result archive, and the paper states the deterministic run-selection rule used to handle short or extra rows. The provided Mosquitto rows do not support the same 24-hour three-way comparison because ChatAFL is absent and the available LoopFuzz rows are substantially shorter than AFLNet and MBFuzzer. The ablation table is likewise an archive-level reconstruction under the same deterministic selection rule rather than a hand-picked replacement set.

\section{Conclusion}
We have shown that fluent protocol text is insufficient for a stateful campaign. What matters is a closed-loop runtime admission boundary that can reject semantically premature generations and refine them when they fail.

Under the audited primary comparison against AFLNet and ChatAFL, LoopFuzz demonstrates a stronger \texttt{edges} profile and a selective \texttt{b\_abs} advantage. On the nine off-the-shelf targets, it achieves the highest mean final \texttt{edges} on all nine targets and the highest mean final \texttt{b\_abs} on eight. The strongest same-target \texttt{b\_abs} evidence appears on Pure-FTPd, Exim, Live555, and Lighttpd1; the strongest \texttt{edges} evidence appears on LightFTP, bftpd, ProFTPD, Pure-FTPd, Exim, and Live555.

The broader baseline picture is mixed. NSFuzz remains strongest on final \texttt{b\_abs} for five of the eight reproduced NSFuzz targets, while LoopFuzz has the highest reported \texttt{edges} on seven of those eight. On MQTT, the available LoopFuzz rows exceed AFLNet in archived \texttt{b\_abs} and \texttt{edges}, but those rows are much shorter. MBFuzzer reports \texttt{branch\_covered} under 24-hour runs in its own artifact format, which is not a direct comparison with the AFLNet-lineage \texttt{b\_abs} field. The archived ablations also do not support a claim that every exposed LoopFuzz sub-control is individually necessary across all targets. The evidence therefore supports a precise conclusion: closed-loop runtime admission control improves state-exploration behavior within the closest AFLNet/ChatAFL lineage and improves absolute branch coverage on most primary targets, but this study does not establish dominance over specialized external fuzzers.
