# Q1–Q3 mock smoke evaluation criteria

## Scope

The cross-target batch is a threshold-1, 15-minute, three-repeat implementation smoke for the eight core arms on all nine targets: lightftp, bftpd, proftpd, pure-ftpd, exim, live555, kamailio, forked-daapd, and lighttpd1. It checks arm configuration, target-specific mock protocol pinning, isolated gateway operation, target resets, archive integrity, and coverage replay. It is not a matched-dose comparison and cannot by itself answer Q1–Q3. The separate Q1–Q3 comparisons require their question-specific treatment arms and mechanism evidence below.

The follow-up comparison is scoped to BFTPD and uses three independent repeats per arm, a 5,000 admitted-target-invocation campaign cap, and a 15-minute wall-clock ceiling. A comparison is fixed-call only if every repeat reaches the configured cap and ends for that reason before the wall-clock ceiling. Otherwise report it as time-censored with actual invocation counts. Q1 no-reflow intentionally reduces its effective cap by parked quota; that reduction is part of the treatment and must be reported, not normalized away.

## Validity checks

An arm passes the smoke only when all three repeats have exit code 0, a saved archive, the expected arm and shared configuration in `run-config.jsonl`, working mock-gateway evidence, successful resets for every executed target call, and a complete coverage-v4 terminal record. A reset cancellation is tolerated only when the same attempt is independently logged as `invocation_refused` with `executed=false` and `fault=resource-limit-not-executed`, the reset is marked cancelled with signal status 15, and the run ends with `signal-or-timeout`; report that terminal refused attempt separately. Any failed reset tied to an executed call or any unexplained reset failure makes the repeat ineligible until repaired and rerun.

Before comparing arms, verify target, seed-corpus hash, target and fuzzer hashes, mock configuration, threshold, campaign cap, and coverage-replay version. Report each repeat, the mean, and sample standard deviation. With three independent mock repeats, use the results as directional smoke evidence; do not claim statistical significance or cross-protocol generality.

## Outcome measures

Coverage is reported as the absolute source-branch count from complete coverage-v4 corpus replay (`b_abs`) and as branch coverage per 1,000 admitted target invocations. The replay count is the accumulated saved-corpus result; it does not identify when a branch was first reached. Also report wall time, charged target calls, LLM requests/tokens, and the mechanism-specific counters below. Higher branch coverage and branch yield are favorable. Lower target calls, LLM cost, or wasted validation dose are favorable only when useful coverage is maintained. The 5,000-call cap counts target invocations; mock campaign requests count LLM interactions and are expected to be much fewer, so they must not be compared as though they were the same dose.

The runner pins `MOCK_PROTOCOL` from the target image map before starting the mock. The archived `effective_config.protocol` must equal the expected protocol, and every request, including startup preflight, must be attributed to that pinned response bank. forked-daapd is tested through its HTTP interface, so its expected protocol family is HTTP. This avoids prompt-content inference when SMTP/RTSP/SIP prompts mention other protocols. Legacy archives with a missing protocol pin are not eligible for strict cross-target conclusions. `truncated` is a subset of HTTP 200 responses, and `reply_classes` counts successful campaign replies while excluding preflight and HTTP errors.

**Q1 — avoid unproductive resource allocation.** Compare `q1a1` direct service with `q1b1` idle, `q1c1` reflow, and `q1d1` reflow plus code-retain. Report configured and effective call caps, charged invocations, saved validation quota, idle quota, reflow consumed and left, validation/provisional calls, and branch yield per 1,000 calls. A favorable direction is positive mean change in branch yield, or comparable branch coverage with fewer charged calls; the saved/idle/reflow ledgers must show that the intended allocation decision occurred. The direct, idle, reflow, and code-retain policies are distinct treatments, so interpret each comparison against its declared baseline.

**Q2 — provisional validation finds value ordinary mutation misses.** Compare `salvage1` with `ordmatch1`, and report salvage attempts/admissions, provisional roots served, descendant calls per root, beyond-trial code gains/conversions, and branch yield. Before interpreting this comparison, link each admitted root to exactly one terminal event and one productivity row using the stable root/candidate identifiers; require the terminal and productivity descendant-call totals to agree. A repeat is answerable only with at least 10 uniquely linked, positively served roots in each cohort, matching target/configuration/campaign budget and the same per-root provisional cap, and a ratio of 0.80–1.25 between the arms' median descendant calls per served root. This is a smoke answerability floor, not a statistical-power claim. If any repeat misses these conditions, report Q2 as unresolved for the three-repeat comparison. For answerable repeats, calculate beyond-trial code gains per 1,000 linked descendant calls as the dose-normalized outcome, alongside the raw gain and dose totals. A favorable direction is a higher mean dose-normalized gain for salvage; mixed repeat directions are unstable evidence.

**Q3 — calibration improves scheduling over simpler online rules.** Compare `calibrated1` with `cal_ewma1`, `cal_run_rate1`, and `wrapgate1`. Each `calibrated1` repeat must contain at least one positive-weight `weighted-eligible` selection with `calibration_applied=true` and `calibration_changed_selection=true`, plus at least one eligible, completed episode with positive reward evidence and a recorded posterior update. For fixed-window rewards, the completed reward window must match the configured width. A zero-trigger or zero-update repeat makes the three-repeat Q3 comparison unresolved. Report the trigger, reward, posterior update, and `calibration_changed_selection` counts. Then compare final source branches and branch yield per 1,000 calls. A favorable direction requires a positive mean coverage/yield change against both simpler online estimators; path activation alone is not an outcome improvement.

For each question, a positive three-run mean difference is a directional signal, not a significance claim. Show all three per-run differences and their spread; mixed directions mean the smoke signal is unstable. A missing mechanism event, unmatched input/configuration, incomplete replay, or wall-clock truncation is reported as unresolved rather than as a favorable or unfavorable effect.
