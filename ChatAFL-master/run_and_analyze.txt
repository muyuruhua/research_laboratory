1. LLM语法/消息模板生成（Hypothesis）
o 输入：RFC片段/抓包样例/服务端响应码与错误信息
o 输出：每类 message 的 grammar（ABNF风格或你自定义CFG/JSON schema）+ 字段约束（长度、枚举、依赖关系）


2. 验证器（Verifier，核心创新点）
不需要形式化证明，可用且“工程上强有效”的验证：
o 可解析性：生成消息能被本地parser解析（CFG/正则/字段拆解）
o 可接受性：发送给SUT后得到“非拒绝类响应”（比如非400/非error）
o 状态可达性：消息序列触发新响应码/新状态节点（可用 State Transition Tree 思路）USENIX’22 的 Stateful Greybox Fuzzing
o 覆盖增益：覆盖/状态覆盖提升才将该grammar片段“入库”

3. 反例驱动修正（Counterexample-guided Refinement）
o 当验证失败：把失败样例（最小化后的请求+响应+差分）回喂给LLM，让它只修一个字段/一条产生式
o 关键：限制LLM自由度（只允许局部patch），降低幻觉

4. 状态导向调度（State-aware Scheduling）
o 把“状态节点/转移”作为 fuzz feedback（类似 stateful greybox fuzzing 的 STT）

🔴 根因 #1：重量级进程启动/关闭（额外 ~900ms/exec）
forked-daapd 是 10 个协议中架构最重的目标。每次执行需要：

启动：dbus 通信 → avahi 服务注册 → SQLite 打开 2 个数据库（songs3.db + cache.db）→ inotify 监控 → 媒体扫描
关闭：avahi 注销 → SQLite journal 清理 → 子进程 signal+reap → inotify 关闭，耗时 >200ms
对比同样 -D 200000 的 lighttpd1（纯内存 HTTP，RSS=6MB），forked-daapd 每次执行多了 ~924ms 开销（1136ms vs 212ms），其中 200ms 的 -D 只占 17.6%，剩余 82% 都是进程自身开销。

🔴 根因 #2：极低稳定性（31-34%）
R1 的 variable_paths = 151 = paths_total，意味着 100% 路径都不稳定！原因是 dbus/avahi 异步通信、SQLite 缓存行为和 inotify 事件竞态导致的执行不确定性。AFL 无法准确判断哪些输入真正有价值。

🟡 根因 #3：R1 peak_rss=3577MB 内存异常
R1 的 LLM enrichment 更激进（100 calls, 83433 tokens → 90 enriched seeds），对比 R2（48 calls, 47304 tokens → 36 enriched seeds）。更多/更复杂的 HTTP 报文可能触发 SQLite 写入路径，导致数据库膨胀和 3577MB 内存峰值。R2 只用了 124MB。

🟡 根因 #4：有限的种子空间
仅 2 个原始种子（都是简单的 HTTP GET），bitmap_cvg 只有 6.9-7.1%。forked-daapd 有丰富的 REST API（/api/library, /api/player, /api/queue, /api/search 等），2 个 GET 种子远不够覆盖。

🟡 根因 #5：pending_favs 溢出
R1 末尾 pending_favs = 4294967294（u32 下溢），说明 favored paths 计数出现异常，可能影响调度效率。

📊 每次执行时间分解
阶段	forked-daapd	lighttpd1
-D server_wait	200ms (17.6%)	200ms (94.3%)

结论：forked-daapd 性能差是目标自身特性决定的（重依赖、非确定性、慢启停），不是 fuzzer 的 bug。这也是为什么 kamailio（0.76 eps）是唯一比它更慢的协议——两者都是依赖复杂的重量级服务器。

综合评估结论如下：

4个协议的影响严重程度
协议	OPT false hangs	覆盖率对比	路径发现对比	影响等级
lighttpd1	251-289 (100% fake)	持平 (6.08% vs 6.12%)	OPT 略低 -15%	⚠️ 中等

关键差异：为什么这4个协议不像 forked-daapd 那样严重？
根本原因是进程退出速度不同：

forked-daapd 收到 SIGTERM 后清理极慢（远超 200ms），导致几乎每次执行都触发 child_force_killed → 几乎所有新覆盖都被错误分类为 FAULT_TMOUT → 新路径写入 virgin_tmout 而非 virgin_bits → 后续相同覆盖不会被识别为新路径 → 路径发现几乎为零

lighttpd1,proftpd,pure-ftpd,exim 收到 SIGTERM 后通常在 200ms 内退出，只有部分执行（可能是服务器忙于处理复杂请求时）会触发 child_force_killed。所以大部分新路径仍然正确进入 virgin_bits，覆盖率正常积累。

结论
严重受影响的只有 forked-daapd — 这是唯一一个 OPT 性能远差于 baseline 的协议
lighttpd1 受中等影响 — false hangs 数量大，路径发现略有下降（-15%），但覆盖率未受损
proftpd/pure-ftpd/exim 仅轻微影响 — false hangs 只浪费磁盘和分类开销，不影响核心覆盖率指标
Fix-14c 对所有协议都有益 — 消除 false hangs 可以提升信噪比，轻微改善路径发现效率，且完全无副作用
